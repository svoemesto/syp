# М-01: связка среды исполнения и видеокарты в контейнере

**Задача**: T075 (замер выполнен по пути T063). **Дата замера**: 2026-10-02.
**Серия**: `GOT.S01E01`, кадры 1920×1080 из настоящей серии.

## Что мерили

Может ли детектор лиц работать **внутри контейнера `syp-admin-app`**: поднимается
ли провайдер вычислений на видеокарте, видит ли контейнер карту и отвечает ли
модель на настоящем кадре серии. Замер сделан **по пути задачи T063**, потому
что без работающего детектора задача не закрывается: замер без детектора был бы
проверкой пустой среды.

## На чём мерили

| Что | Значение |
|---|---|
| Машина | `nsa-i9`, Intel Core i9-10980XE, 36 ядер, 62 ГиБ ОЗУ |
| Карта | NVIDIA GeForce RTX 4060 Ti, 15,53 ГиБ, возможности `8.9` |
| Драйвер | 580.178.04; версия CUDA в драйвере 13.0 |
| Образ для проверки | `python:3.12-slim`, одноразовый контейнер, ключ `--gpus all` |
| Модель | `face_detection_yunet_2023mar.onnx`, 232 589 байт, MIT |
| Число прогонов | по одному на каждую комбинацию среды; повторов по времени детекции **не делалось** |
| Карта в момент замера | **занята посторонними процессами** (17 % загрузки, 2717 МиБ из 16 ГиБ до начала замера) — числа по времени искажены |

**Замер сделан в одноразовом контейнере, а не в `syp-admin-app`:** контейнеры
SYP в этой сессии не создаются, а правило замера 3 каталога `measurements`
прямо предписывает одноразовый контейнер с удалением. Проверка
`docker exec syp-admin-app nvidia-smi` **не выполнялась** — контейнер
`syp-admin-app` не создавался.

## Какое число получили

### 1. Карта видна контейнеру

```
$ docker run --rm --gpus all python:3.12-slim nvidia-smi -L
GPU 0: NVIDIA GeForce RTX 4060 Ti (UUID: GPU-0bde36ab-4814-4fa2-0a52-00f7f56a7399)
```

### 2. Среды исполнения на машине администратора достаточно, но не такой версии

Виртуальное окружение `/home/nsa/syp/.data/venv-gpu` проверено фактами:

| Проверка | Результат |
|---|---|
| `torch.__version__` | `2.11.0+cu128` |
| `torch.cuda.is_available()` | `True` |
| Вычисление на CUDA | выполнено, контрольная сумма получена |
| `onnxruntime.__version__` | `1.30.0` |
| `ort.get_available_providers()` | `['TensorrtExecutionProvider', 'CUDAExecutionProvider', 'CPUExecutionProvider']` |
| `CUDAExecutionProvider` **фактически поднят** | **нет** |

Последняя строка — существенная. Сборка `onnxruntime-gpu` 1.30.0 с PyPI собрана
под CUDA 13, а в окружении лежат библиотеки CUDA 12 (`nvidia-cublas-cu12` и
остальные `-cu12` от `torch`). `get_available_providers()` перечисляет
`CUDAExecutionProvider` **по факту компиляции**, а не по факту загрузки
библиотек, поэтому список здесь вводит в заблуждение: при создании сессии
провайдер не поднимается и onnxruntime **молча** уходит на CPU. Текст отказа:

```
libcublasLt.so.13: cannot open shared object file: No such file or directory
Require cuDNN 9.* and CUDA 13.*
провайдеры сессии: ['CPUExecutionProvider']
```

То же повторилось в одноразовом контейнере с `onnxruntime-gpu==1.30.0` и
колёсами CUDA 13: `nvidia-cublas==13.8.1.7` и остальные поставились, но
`libcublasLt.so.13` не нашёлся. Причина найдена в коде onnxruntime: для CUDA 13
библиотеки ищутся по **консолидированной** раскладке `nvidia/cu13/lib`
(`onnxruntime/__init__.py`, функция `_get_nvidia_dll_paths`), а колела с такой
раскладкой на PyPI не опубликованы: пакет `nvidia-cu13` отдаёт 404.

### 3. Рабочая связка найдена

Сборка `onnxruntime-gpu` **1.29.0** под CUDA 12 с опубликованными колелами
`-cu12` поднимает провайдер:

```
onnxruntime 1.29.0
доступные провайдеры: ['TensorrtExecutionProvider', 'CUDAExecutionProvider', 'CPUExecutionProvider']
провайдеры сессии: ['CUDAExecutionProvider', 'CPUExecutionProvider']
```

проверка «провайдер вычислений инициализируется». Список **доступных**
провайдеров для этой проверки не годится — см. пункт 2.

### 4. Детектор отвечает на настоящем кадре

Кадр 1920×1080 из `GOT.S01E01` (6 220 800 байт `bgr24`), модель YuNet, вход
640×640, порог уверенности 0,6, провайдер `CUDAExecutionProvider`:

| Что | Значение |
|---|---|
| Провайдер в строке приветствия | `CUDAExecutionProvider` |
| Найдено лиц | **7** |
| Наибольшая рамка | (254, 679) — (445, 827) |
| Меньшая рамка | (827, 381) — (874, 411), 47×30 пикселей |
| Уверенность | от 0,77 до 0,82 |
| Время вывода **первого** кадра | 2008 мс |
| Код завершения программы детектора | 0 |

Время первого кадра **не является временем детекции**: в него входят создание
контекста CUDA и загрузка ядер. Установившееся время на этой серии **не
измерено** — это работа М-02 (задача T076), и здесь она не выполнялась.

### 5. Порог уверенности на двадцати кадрах серии

Двадцать кадров, выбранных равномерно по серии, вычисления на CPU (карта была
занята, и на CPU числа сравнимы между собой):

| Порог уверенности | Кадров с лицами из 20 | Всего лиц | Площадь рамки, пикселей² |
|---|---|---|---|
| 0,9 | **0** | 0 | — |
| 0,7 | 7 | 20 | 325…37 800 |
| 0,6 | 12 | 36 | 264…37 800 |
| 0,5 | 15 | 45 | 264…38 115 |
| 0,4 | 15 | 50 | 150…38 115 |

Порог 0,9 — исходный из репозитория модели — на двадцати кадрах не находит
**ни одного** лица. Рабочее значение по умолчанию взято 0,6: это исходное
значение из `yunet.py` модели, и на двадцати кадрах оно даёт правдоподобные
рамки.

**Это не подбор порога.** Критерий М-02 — доля ненайденных лиц на 200 кадрах
и время на 1000 кадров, проверенные вручную; здесь измерено только то, что
детектор вообще работает, и выбранное значение по умолчанию не является
настройкой сериала. Ложные срабатывания на этих двадцати кадрах **не
проверены** — вручную кадры не смотрелись.

### 6. Бэкенд админки с детектором поднимается в контейнере

Собран настоящий образ `deploy/Dockerfile.backend` и запущен контейнер из
него: одноразовая база `postgres:16` с миграциями 01…11 и сам бэкенд с
`--gpus all` и переменными окружения детектора.

| Что | Значение |
|---|---|
| Состояние контейнера | `Up` |
| Журнал | `Tomcat started on port 7911`, `Started AdminApplicationKt in 2.373 seconds` |
| `nvidia-smi -L` внутри контейнера | `GPU 0: NVIDIA GeForce RTX 4060 Ti` |
| Программа детектора внутри контейнера | `{"status": "ready", ..., "provider": "CUDAExecutionProvider", "onnxruntime": "1.29.0", ...}` |
| Вес образа `svoemesto/syp-admin-app:local` | **6,78 ГиБ** |

**Два дефекта найдены этим запуском и исправлены.** Оба были незаметны для
тестов: тесты собирают бины по частям, а контекст целиком не поднимался ни
разу.

1. **Два бина с именем `externalProgram`.** В одном контексте имя бина
   повторяется, и Spring отказывается стартовать: `A bean with that name has
   already been defined ... and overriding is disabled`. Объявление осталось
   одно, внедрение идёт по типу.
2. **Значения по умолчанию у параметров метода `@Bean`.** У
   `adminJobWorker` два параметра имели значения по умолчанию, а Spring ищет
   фабричный метод **без аргументов**: `No matching factory method found ...
   factory method 'adminJobWorker()'`. Значения читаются теперь внутри тела
   метода — так же, как это сделано в остальных бинах сборки.
3. **Каталога `/data` в образе не было.** Значения по умолчанию для
   промежуточных файлов и артефактов указывают на `/data/syp-work` и
   `/data/syp-storage`, а процесс контейнера работает не от root и создать
   каталог не может: `AccessDeniedException: /data`. Каталоги создаются в
   образе и принадлежат пользователю контейнера.

## Каким критерием проверяется

Критерий М-01 (T075): «провайдер вычислений инициализируется, кадр обработан,
`nvidia-smi` из контейнера показывает карту».

**Вывод: критерий выполнен по существу, одна проверка не выполнена.**

| Проверка критерия | Состояние | Чем подтверждено |
|---|---|---|
| Провайдер вычислений инициализируется | **выполнено** | `провайдеры сессии: ['CUDAExecutionProvider', ...]` в одноразовом контейнере с `--gpus all` |
| Кадр обработан | **выполнено** | 7 рамок на настоящем кадре 1920×1080, код завершения 0 |
| `nvidia-smi` из контейнера показывает карту | **выполнено в одноразовом контейнере** | `GPU 0: NVIDIA GeForce RTX 4060 Ti` |
| `docker exec syp-admin-app nvidia-smi` | **выполнено в одноразовом контейнере из того же образа** | `GPU 0: NVIDIA GeForce RTX 4060 Ti` (см. пункт 6) |
| Детектор стартует **внутри контейнера админки** | **выполнено** | контейнер поднялся, `Started AdminApplicationKt`, программа детектора изнутри него отвечает `CUDAExecutionProvider` (см. пункт 6) |
| Седьмого контейнера не появилось | **выполнено** | в `deploy/docker-compose.yml` сервисов по-прежнему шесть; проверочные контейнеры одноразовые и удалены |

## Модель детектора

| Что | Значение |
|---|---|
| Модель | YuNet (`face_detection_yunet_2023mar.onnx`) |
| Источник | [opencv_zoo/models/face_detection_yunet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet) |
| Вес | **232 589 байт** (227 КиБ) |
| Лицензия | **MIT**, `(c) 2020 Shiqi Yu`; текст лежит в `deploy/models/LICENSE-face_detection_yunet.txt` |
| Сумма sha256 | `8f2383e4dd3cfbb4553ea8718107fc0423210dc964f9f4280604804ed2552fa4` |
| Вход сети | 640×640, в модели зашит |
| Заявленная точность | AP 0,884 / 0,866 / 0,750 на WIDER FACE (easy / medium / hard) — цифра авторов модели, на `GOT.S01E01` не проверялась |
| Ограничение модели | лица размером примерно от 10×10 до 300×300 пикселей — из способа обучения |

Почему эта модель, а не другие:

- **вес 232 КиБ** — на порядок меньше любой большой сети; в образ попадает
  файл, который не жалко держать в git-исключениях и который не утяжеляет
  сборку;
- **MIT** — разрешение без оговорок о некоммерческом применении. Это отсекает
  основных кандидатов: веса SCRFD и ArcFace из InsightFace распространяются с
  ограничением на некоммерческое использование, а YOLO-линейка — под AGPL;
  и то и другое для продукта неприемлемо без отдельного решения владельца;
- **onnxruntime без отдельного фреймворка**: Torch ради одного вывода не
  нужен, а образ с ним весит в разы больше;
- **динамика обучения допускает дообучение под сериал** позже, когда появится
  выбор моделей (T076).

Файл модели **не коммитится**: `deploy/models/*.onnx` в `.gitignore`. Лицензия
рядом с ним коммитится — лицензия обязана быть в репозитории, файл модели —
нет.

## Что это означает для плана

1. **Версии среды в контейнере и на машине разошлись**: в образе 1.29.0 под
   CUDA 12, в окружении машины 1.30.0 под CUDA 13, у которой нет
   опубликованных колёл. Это осознанный выбор (единственная стабильная
   ставится), но он требует решения владельца, если версии должны совпадать.
2. **Список доступных провайдеров — не проверка.** Он содержит
   `CUDAExecutionProvider` и в том случае, когда провайдер не поднялся. Проверка
   в коде детектора смотрит на провайдеры **сессии** и объявляет уход на CPU
   отказом: молчаливый уход на CPU выглядел бы как «просто медленно», а на
   88 643 кадрах это часы вместо минут.
3. **Детектор умеет считать лица, но качество его не измерено.** Следующий
   шаг по качеству — М-02 (T076): 2—3 кандидата на 2000 кадрах, доля
   ненайденных лиц вручную на 200 кадрах, время на 1000 кадров.
4. **Время вывода не измерено на установившемся потоке.** Число 2008 мс
   относится к первому кадру и включает подъём контекста CUDA.

## Как повторить

```sh
# Проверка среды в одноразовом контейнере с картой.
# Полный сценарий: /home/nsa/syp/.data/detector/runtime-check.sh <модель> <кадр>

docker run --rm --gpus all python:3.12-slim nvidia-smi -L

# Прогон программы детектора вручную: кадр подаётся на стандартный ввод,
# ответ приходит на стандартный вывод.
ffmpeg -hide_banner -nostdin -ss 600 -i "$SRC" -frames:v 1 -pix_fmt bgr24 -f rawvideo frame.raw -y
syp_face_detector.py --model face_detection_yunet_2023mar.onnx --provider CUDAExecutionProvider \
    --input-width 640 --input-height 640 --score-threshold 0.6 < frame.raw
```
