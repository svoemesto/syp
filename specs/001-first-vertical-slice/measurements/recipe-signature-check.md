# Проверка подписи сценария сторонним инструментом

**Задача**: T133. **Дата прогона**: 2026-10-03. **Машина**: `nsa-i9`.
**Инструмент**: `OpenSSL 3.0.13 30 Jan 2024 (Library: OpenSSL 3.0.13)`.

Подпись ставит код проекта (`syp-core/…/signing/Signer.kt`), а проверяет её
**не тот же код** — иначе ошибка канонизации осталась бы незамеченной: код,
который неверно определяет «что подписано», так же неверно это и проверяет
(компонент `recipe-signer`, раздел «Интерфейсы и Контракты»).

Проверка живёт постоянно, а не разово: `OpenSslVerificationTest` в
`syp-core/src/test/kotlin/ru/svoemesto/syp/core/signing/`. Прогон:

```
GRADLE_USER_HOME=/home/nsa/syp/.gradle ./gradlew :syp-core:test --tests '*OpenSslVerificationTest*'
```

## Что проверяется

1. Сценарий подписывается ключом Ed25519, ключ приходит в `base64` из
   `SYP_SIGNING_PRIVATE_KEY` тем же разборщиком, что и на сервере.
2. Канонические байты кладутся в файл **без изменений**.
3. Открытый ключ записывается в `public.pem` — в том виде, в каком его
   отдаёт `GET /api/recipes/verification-key`.
4. Подпись кладётся в отдельный файл: она хранится вне подписываемого файла
   (контракт рецепта, раздел 3).

## Команды и вывод

Каталог во время прогона одноразовый и удаляется в конце; пути ниже — из
реального вывода теста.

**Проверка подписи:**

```
openssl pkeyutl -verify -pubin -inkey /tmp/syp-signature-check-…/public.pem \
  -rawin -in /tmp/syp-signature-check-…/recipe.syp-recipe.json \
  -sigfile /tmp/syp-signature-check-…/recipe.sig
```

```
Signature Verified Successfully
код возврата: 0
```

**Проверка того же файла с изменённым одним байтом:**

```
openssl pkeyutl -verify -pubin -inkey /tmp/syp-signature-check-…/public.pem \
  -rawin -in /tmp/syp-signature-check-…/tampered.syp-recipe.json \
  -sigfile /tmp/syp-signature-check-…/recipe.sig
```

```
Signature Verification Failure
код возврата: 1
```

## Вывод

- Подпись, выданная сервером, проверяется **сторонним инструментом** и
  проверяется успешно.
- Изменение одного байта после подписания обнаруживается: `openssl` отказывает
  с кодом `1` (свойства 1 и 2 контракта `recipe-format.md`).
- Формат ключа совпадает с тем, что отдаёт публичная часть: PEM, а не голый
  base64. Причина — `openssl pkeyutl` читает файл открытого ключа именно в
  этом виде, и отдав base64, пришлось бы собирать файл на стороне пользователя.

## Чего здесь нет

- **Проверки на машине пользователя нет**: выполнялась на машине администратора
  тем же инструментом, которым будет проверяться воркер. Сценарий «файл прошёл
  через браузер и диск, подпись не сошлась» на машине пользователя проверяется
  задачей T158 вместе с остальными свойствами контракта.
- **Числа прогонов нет**: проверка детерминированная, повторять её три раза
  ради разброса нечего. Единственное, что здесь не измерено, — присутствие
  `openssl` на конкретной машине пользователя: без него тест **пропускается**,
  а не падает, и пропуск виден в отчёте.
