# Контракт: HTTP API админки (`syp-admin-app`)

**Feature**: 001-first-vertical-slice
**Потребитель**: `syp-admin-web` (Vue 3) и только он.
**Транспорт**: HTTP/1.1, JSON, префикс `/api`. Аутентификации в первый срез
нет — стек локальный (решение владельца, `spec.md` «Assumptions»).
**Документация**: каждый публичный метод документирован, ссылка на этот файл
обязательна (FR-100). Per-feature документ — [`../../../../docs/features/first-vertical-slice.md`](../../../docs/features/first-vertical-slice.md) (FR-101).

**Граница (ADR-0009, ADR-0014).** В админке **нет** ни одного способа
собрать подборку: готовый видеофайл делает машина пользователя из своей копии
исходников (FR-085).

Сценарий сборки, наоборот, **выдаётся админкой**: генерация и подпись
выполняются там, где живёт закрытый ключ подписи, а публичная часть только
читает уже подписанное и хранимое (ADR-0014, решение владельца 2026-10-03).
Раздел 10 описывает эту выдачу целиком.

## 1. Общие правила

1. **Коды ответов**: `200` — успех, `201` — создан ресурс, `202` — работа
   принята в очередь (ответ содержит идентификатор задания), `400` — ошибка
   запроса, `404` — ресурс не найден, `409` — конфликт состояния, `422` —
   запрос понят, но невыполним (например, несовместимые эпизоды в подборке),
   `500` — внутренняя ошибка с текстом.
2. **Тело ошибки всегда** содержит машинный код, человекочитаемое сообщение
   на русском и, если уместно, перечень проблемных объектов. Пустой ответ с
   кодом 500 без текста запрещён: ошибка обязана выглядеть как ошибка
   (constitution IV.2).
3. **Время** в ответах — только вычисленное, производное от номера кадра и
   `time_base` эпизода. Клиент не хранит и не передаёт время как источник правды
   (ADR-0001).
4. **Нумерация кадров с нуля** в обоих направлениях (ADR-0001,
   `research.md` Т-12).
5. **Пагинация** списков: `offset`, `limit` (по умолчанию 200, максимум 2000).
   Списки кадров и лиц пагинируются всегда — на эпизоде их десятки тысяч.

## 2. Справочник типов ошибок

| Код | Когда | Что делает интерфейс |
|---|---|---|
| `JOB_NOT_RUNNABLE` | предпосылки задания не выполнены | показать, чего не хватает |
| `INCOMPATIBLE_EPISODE` | эпизода подборки несовместимы для склейки без перекодирования | показать перечень и различающиеся признаки |
| `CHECKSUM_NOT_READY` | у эпизода нет актуальный суммы `sha256` | показать состояние и предложить поставить пересчёт |
| `EPISODE_NOT_ANALYZED` | у эпизода нет сцен с размеченными границами | `409` с состоянием анализа |
| `EMPTY_SELECTION` | в запросе нет ни одной сцены | `400` с текстом |
| `UNKNOWN_CONDITION_TYPE` | тип условия фильтра вне белого списка | показать текст; **не** показывать пустой результат |
| `FILTER_TOO_DEEP` | глубина дерева фильтра больше трёх уровней | показать текст |
| `SOURCE_UNREADABLE` | файл эпизода недоступен | показать путь и текст ошибки |
| `BOUNDARY_CONFLICT` | граница внутри диапазона не согласована | показать конфликтующие диапазоны |
| `STALE_RESULT` | результат помечен устаревшим | предложить пересчёт, **не** стирать правки |

`POST /api/movies` — тело `{"name": "Игра престолов", "sourceRoot": "/sources"}`; ответ `201` с
созданным фильмом **и со значениями настроек по умолчанию**: настройки
создаются автоматически, оператор их правит (ADR-0003, `research.md` Т-06).

### 3.2 Сезоны

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/movies/{movieId}/seasons` | сезоны фильма с номерами эпизодов |
| `POST` | `/api/movies/{movieId}/seasons` | завести сезон: `{"ordinal": 1, "name": "Первый сезон"}` |

Номер сезона начинается с единицы и уникален внутри фильма. У художественного

### 3.3 Эпизода

| Метод | Путь | Назначение | FR |
|---|---|---|---|
| `GET` | `/api/movies/{movieId}/episodes` | список эпизодов | FR-001 |
| `POST` | `/api/movies/{movieId}/episodes` | зарегистрировать эпизод: путь к файлу; путь обязан лежать внутри корня фильма | FR-001, FR-002, FR-089a |
| `GET` | `/api/episodes/{episodeId}` | параметры эпизода и состояние готовности | FR-002 |
| `DELETE` | `/api/episodes/{episodeId}` | снять эпизод с учёта (файл не трогается) | — |

`POST /api/movies/{movieId}/episodes` — тело
`{"sourcePath": "...", "seasonId": 1, "episodeOrdinal": 3}`. `seasonId` необязателен — у фильма его нет; `episodeOrdinal` по умолчанию `0`, отрицательные отвергаются кодом `BAD_REQUEST`. Ответ содержит `designation` вида `S02E03`, а у фильма — `S00E00`..
Сервер опрашивает файл и **сам** определяет параметры (FR-002): число кадров,
частокадровую базу, разрешение, длительность, кодек, профиль, формат
пикселей, параметры аудио, карту ключевых кадров. Ответ `201` с полным
набором параметров. Если файл недоступен — `400` с кодом
`SOURCE_UNREADABLE`: это ошибка, а не «успех с пустым результатом».

### 3.4 Сверка целостности исходника

Справочник сумм — эталон проверки на машине пользователя (ADR-0009). Он
заполняется при регистрации эпизода автоматически и пересчитывается по кнопке.

| Метод | Путь | Назначение | FR |
|---|---|---|---|
| `GET` | `/api/episodes/{episodeId}/checksum` | состояние суммы, алгоритм, значение, дата подсчёта, признак устаревания | FR-089 |
| `POST` | `/api/episodes/{episodeId}/checksum` | поставить пересчёт заданием `HASH` | FR-089, FR-003 |

Ответ `GET`:

```json
{
  "episodeId": 7,
  "state": "DONE",
  "algorithm": "SHA-256",
  "digest": "3f786850e387550fdab836ed7e6dc881de23001b…",
  "byteSize": 5600000000,
  "fileMtime": "2026-09-14T10:21:00Z",
  "computedAt": "2026-10-02T11:03:22Z",
  "isStale": false
}
```

Инварианты ответа: у эпизода не может быть двух актуальных сумм; при
`state = "DONE"` поле `computedAt` заполнено; при `state = "ERROR"` —
заполнено `errorText`.

### 3.4 Настройки анализа

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/movies/{movieId}/settings` | текущие пороги, параметры кластеризации, версия формата сценария, число аудиодорожек |

```json
{
  "id": 412,
  "kind": "FACES",
  "state": "WORKING",
  "subject": {"type": "EPISODE", "id": 7},
  "progress": {"done": 51230, "total": 82834, "note": "кадр 51230 из 82834"},
  "error": null,
  "createdAt": "2026-10-05T09:12:03Z",
  "startedAt": "2026-10-05T09:12:04Z",

```

после сбоя внешней программы (FR-004, SC-005).

### 5.1 Границы и происхождение

Границы сцены и плана в ответе содержат номера кадров, вычисленное время и
происхождение:

```json
{
  "scene": {
    "id": 90,
    "firstFrame": 1200,
    "lastFrame": 4180,
    "origin": "OPERATOR",
    "location": {"id": 3, "name": "Лагерь Джейми"},
    "isStale": false,
    "shots": [
      {"id": 900, "firstFrame": 1200, "lastFrame": 1455,
       "size": "MCU", "sizeOrigin": "AUTO", "origin": "AUTO", "isStale": false}
    ]
  }
}
```

`origin` определяет цвет оверлея: `AUTO` — красный (алгоритм), `OPERATOR` —
зелёный (оператор), `CANCELLED` — оранжевый (решение алгоритма отменено)
(FR-015, FR-016).

### 5.2 Превью кадров

| Метод | Путь | Назначение | FR |
|---|---|---|---|
| `GET` | `/api/episodes/{episodeId}/preview-sheets/{index}` | лист превью: 16×16 ячеек по 135×75 | FR-020, FR-022 |
| `GET` | `/api/episodes/{episodeId}/preview-url` | адрес листа для прямой загрузки интерфейсом | FR-020 |

Матрица кадров разрывает строку на границе плана и показывает план на стыке
страниц (FR-022). Состав страницы вычисляет сервер по размеру окна,
приведённому в запросе, и возвращает номера кадров вместе с адресом листа и
областью кадрирования: клиенту не нужно знать раскладку листа.

`GET …/preview-url` принимает `index` **или** `frame`: номер листа нужен
навигации, кадр — переходу к кадру, и переход к кадру с другого листа это один
вызов, потому что сервер сам определяет нужный лист. Ответ содержит номер
найденного листа, поэтому клиенту не нужно знать раскладку.

`GET …/preview-url` отдаёт `sheetCount` — сколько листов у эпизода всего.
Число вычисляется из числа кадров эпизода и раскладки, а раскладка принадлежит
серверу: собирать его на клиенте означало бы продублировать серверное правило
и разойтись с ним при смене настройки. Без него навигация по листам не знает,
где конец.

### 7.1 Инвариант доводки

Любая операция этого раздела меняет границы плана или сцены. Контракт
гарантирует, что в той же операции:

1. **согласуются пересекающиеся сцены** — сцена, внутри которой оказалась
   новая граница, разрезается или сокращается;
2. **пересчитывается принадлежность лиц планам** в затронутом диапазоне, и
   после операции она совпадает с правилом диапазонов (FR-034);
3. **лица с происхождением `OPERATOR` не удаляются** (SC-006);
4. ответ содержит обновлённую структуру затронутого участка — интерфейс не
   перезапрашивает всё дерево.

При нарушении согласованности операция откатывается с кодом `409` и
`BOUNDARY_CONFLICT`; промежуточного состояния не остаётся.

Правила доводки **границы сцены**, которые следуют из инварианта «план лежит в
сцене целиком» (ADR-0007):

1. **Граница сцены встаёт только на границу плана.** Кадр вне плана или внутри
   него отвергается кодом `BOUNDARY_CONFLICT`: сцена, разрезавшая план,
   оставила бы в базе состояние, которого быть не может. У эпизода без планов
   проверки нет — разделять нечего.
2. **Сдвиг ограничен двумя соседними сценами.** Граница может встать в любое
   место между первым кадром первой сцены и последним кадром второй; выход за
   последний кадр второй отвергается, потому что первая сцена накрыла бы начало
   третьей. Чтобы отдать кадры второй сцене, сцены объединяют.
3. **Строка, выведенная из работы, не удаляется.** Поглощённая при объединении
   и исходная при разделении сцена помечаются устаревшими: предложение машины и
   решение человека остаются в базе рядом (FR-093). Рабочей структурой считаются
   строки с `isStale = false`.
4. **У затронутых сцен `origin` становится `OPERATOR`, ссылка на прогон
   обнуляется.** У решения человека нет породившего его прогона, и устаревать
   ему не от чего.
5. **Название и место действия остаются у части, содержащей первый кадр
   исходной сцены.** Вторая часть остаётся без них.
6. **Диапазоны планов не меняются**, поэтому принадлежность лиц планам
   пересчитывать не по чему: копия `shot_id` соответствует вычисленному
   значению, пока границы плана прежние (FR-034).

Ответ операции над границей сцены:

```json
{
  "episodeId": 12,
  "frame": 300,
  "action": "SPLIT",
  "actionTitle": "сцена разделена на две",
  "scenes": [{"id": 91, "firstFrame": 240, "lastFrame": 299, "origin": "OPERATOR", "isStale": false,
              "shots": [{"id": 900, "firstFrame": 240, "lastFrame": 299, "size": "MCU"}]}],
  "supersededSceneIds": [90],
  "scenesTotal": 819,
  "shotsTotal": 1114,
  "frameCount": 88643
}
```

### 7.2 Места действия

Место действия назначается **только вручную**; автоматического определения в
контракте нет (FR-052). `PUT /api/scenes/{sceneId}/location` с пустым телом
снимает назначение.

## 8. Обучение и версии модели

| Метод | Путь | Назначение | FR |
|---|---|---|---|
| `POST` | `/api/movies/{movieId}/training` | поставить обучение: порог и состав эталонов | FR-061, FR-065 |
| `GET` | `/api/movies/{movieId}/model-versions` | версии: дата, число эталонов, состав классов, активность | FR-062 |
| `POST` | `/api/model-versions/{id}/activate` | сделать версию активной | FR-064 |
| `POST` | `/api/model-versions/{id}/rollback` | откат: новая версия на прежнем составе эталонов | FR-064, SC-009 |
| `GET` | `/api/model-versions/{id}` | состав версии | FR-062 |

`POST /api/movies/{movieId}/training` — тело
`{"threshold": 0.5, "movieIdOfExamples": null}`. Ответ `202`: обучение идёт
заданием очереди, кнопка не блокирует интерфейс (FR-061). Порог приходит из
запроса и сохраняется в версии модели, а не зашивается в код (FR-065).

Откат не удаляет и не переписывает предыдущие версии: он создаёт **новую**
версию на том же составе эталонов, что и указанная версия, и делает её
активной. Прежние метки распознавания при этом восстанавливаются без
повторного обучения оператором (SC-009).

Тело дерева:

```json
{
  "name": "Джейми в лагере, крупно",
  "root": {
    "conjunction": "AND",
    "conditions": [
      {"type": "LOCATION", "subject": "SCENE", "operator": "IN", "value": [3], "negated": false}
    ],
    "groups": [
      {
        "conjunction": "OR",
        "conditions": [
          {"type": "PERSON", "subject": "SHOT", "operator": "IN", "value": [12], "negated": false},
          {"type": "SHOT_SIZE", "subject": "SHOT", "operator": "IN", "value": ["CU", "BCU"], "negated": false}
        ],
        "groups": []
      }
```

`type` принимает значения FR-073: `PERSON`, `LOCATION`, `SHOT_TYPE`,

результат (ADR-0008). Глубина вложенности больше трёх уровней отвергается с
`FILTER_TOO_DEEP`.

## 10. Выдача сценария сборки

Сценарий **выдаёт админка**: генерация и подпись выполняются там, где живёт
закрытый ключ подписи. Публичная часть только читает уже подписанное и
хранимое — эндпоинта создания у неё нет (ADR-0014, решение владельца
2026-10-03).

Сборку подборки админка по-прежнему не выполняет: готовый видеофайл делает
машина пользователя из своей копии исходников (FR-085, ADR-0009).

| Метод | Путь | Назначение | FR |
|---|---|---|---|
| `GET` | `/api/recipes` | список сценариев фильма: имя, состояние, число фрагментов, расчётные величины, признак устаревания | FR-084 |
| `GET` | `/api/recipes/{recipeId}` | сценарий: состав фрагментов, ожидаемая длительность и кадры | FR-084, FR-083 |
| `POST` | `/api/recipes` | выдать сценарий по выбранным сценам | FR-080, FR-086, FR-089c |

### 10.1 Выдача сценария

`POST /api/recipes` — тело `{"name": "Джейми — выходы", "sceneIds": [1, 4, 9]}`.
Фильм определяется сценами; сцены разных фильмов в одном запросе дают `400`
с кодом `BAD_REQUEST` — подборка собирается внутри одного дерева каталогов.

Порядок проверок **до** создания сценария, в порядке возрастания стоимости
отказа:

1. **Список не пуст.** Иначе `400` с `EMPTY_SELECTION`.
2. **Эпизодом разбираемы.** У всех эпизодов есть сцены с размеченными границами.
   Иначе `409` с `EPISODE_NOT_ANALYZED` и состоянием анализа.
3. **Совместимость.** Разрешение, кодек, профиль, формат пикселей, частокадровая
   база, параметры аудио совпадают у всех involved эпизодов. Иначе `422` с
   `INCOMPATIBLE_EPISODE` и перечнем различающихся признаков.
4. **Эталонные суммы.** У всех involved эпизодов есть актуальный сумма `sha256`.
   Иначе `409` с `CHECKSUM_NOT_READY`: выдать сценарий, который у пользователя
   упадёт через час работы, нельзя (ADR-0009, последствие 4).

Тело ошибки несовместимости — то же, что описывает публичный контракт
[`public-api.md`](public-api.md) § 4.1: `differingAttributes` и список эпизодов с
различающимися признаками. Формат ответа не расходится между бэкендами.

Все четыре проверки идут по метаданным, дополнительных проходов по видео не
требует, и **ни одна из них не ставит выдачу в очередь**: операция над
метаданными выполняется сразу (FR-003, research.md Т-20).

Успешный ответ — `201`:

```json
{
  "recipeId": 55,
  "name": "Джейми — выходы",
  "state": "DONE",
  "schemaVersion": 2,
  "isStale": false,
  "itemCount": 2,
  "expectedDurationMs": 412000,
  "expectedFrameCount": 9876,
  "contentSha256": "9f2c…",
  "signingKeyId": "syp-2026-10",
  "downloadUrl": "/api/recipes/55/file"
}
```

`downloadUrl` указывает на эндпоинт публичной части: файл отдаёт она, а
админка его создаёт. Расчётная длительность и число кадров считаются по сумме
**фактических** границ фрагментов (ADR-0006, FR-083).

**Сценарий `DONE` — уже подписанный и уже записанный.** Подпись Ed25519 ставится
над каноническими байтами, канонические байты кладутся в артефакт, и запись
переводится в `DONE` только после того, как артефакт перешёл в состояние
`READY`: незавершённый файл не считается готовым (FR-091). У админки **есть**
закрытый ключ подписи — в этом её отличие от публичной части, и в этом смысл
решения (ADR-0014).

Ответ содержит **идентификатор** ключа, а не сам ключ: закрытая половина не
покидает контейнер админки ни при каких настройках (ADR-0011, FR-089c).

### 10.2 Помечание устаревания при смене версии формата

Перед выдачей сценарии фильма, созданные при **другой** версии формата,
помечаются устаревшими. Пометка ничего не удаляет: сценарий, его файл, подпись
и идентификатор ключа остаются на месте, и ранее выданный сценарий остаётся
проверяемым по своему ключу, пока он в списке доверенных (FR-090, ADR-0014).

Признак устаревания виден в `GET /api/recipes` и `GET /api/recipes/{recipeId}`
полем `isStale`. Устаревший сценарий **не запрещён**: его по-прежнему можно
скачать и проверить, но пересчитывает его оператор.

## 11. Что в контракт не входит

- **Аутентификация и учётные записи** — вне объёма среза.
- **Операции обучения моделей в публичной части** — разграничение
  ответственности контейнеров запрещено нарушать (Hard Gate «Двух-фронтенд»
  в `AGENTS.md`).
- **Сборка за пользователя из админки** — FR-085 прямо запрещает: готовый
  видеофайл делает машина пользователя.
- **Хранение или выдача готового видео** — FR-088 прямо запрещает.
- **Прямое редактирование размера плана в публичной части** — только
  просмотр результата.
- **Выдача сценария в публичной части** — запрещено ADR-0014: подпись
  выполняется там, где живёт закрытый ключ, то есть в админке. У публичного
  бэкенда нет ни эндпоинта создания, ни закрытого ключа.
