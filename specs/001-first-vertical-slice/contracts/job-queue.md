# Контракт: очередь заданий и запуск внешних программ

**Feature**: 001-first-vertical-slice
**Нормативная основа**: constitution IV, ADR-0006, ADR-0009, `research.md`
Т-10, Т-15, Т-17, Т-20, Т-24.
**Требования**: FR-003, FR-004, FR-089, FR-090, FR-091, FR-092; критерии SC-005,
SC-006, SC-012.

Этот контракт — самый важный для надёжности среза. В старом проекте **ни один
из двенадцати вызовов внешней программы не проверял код возврата**, и
прерванный процесс помечался как «сделано» (`.scratch/syp/research/01b-video-pipeline.md`,
раздел D.4). Здесь это запрещено на уровне контракта.

## 1. Состояния задания

Ровно пять состояний, ровно в этом наборе — так же, как в правилах очереди
проекта:

| Состояние | Что означает | Кто ставит |
|---|---|---|
| `WAITING` | задание в очереди, ещё не взято | постановка в очередь |
| `CREATING` | взято воркером, идёт подготовка | воркер при захвате |
| `WORKING` | идёт собственно работа | воркер |
| `DONE` | работа завершена **и все внешние программы вернули нулевой код** | воркер |
| `ERROR` | работа не удалась | воркер |

Переходы:

```
WAITING ──захват воркером──► CREATING ──начало──► WORKING ──успех──► DONE
   │                             │                       │
   │                             └───────► ERROR ◄───────┘
   └─────────────────────────────────────────────────► ERROR (отмена оператором)
```

Переход в `ERROR` из любого состояния. Возврат из `ERROR` в `WAITING` — только
явным повтором постановки: молчаливый автоматический повтор скрывает
неисправность, а SC-005 требует, чтобы ошибка была видна.

## 2. Виды заданий

| Вид | Что делает | Требования |
|---|---|---|
| `ANALYZE` | границы сцен и планов, листы превью, карта ключевых кадров | FR-010, FR-011, FR-020, FR-022, FR-023 |
| `FACES` | поиск лиц в каждом кадре, эмбеддинги, кластеры | FR-030, FR-031, FR-036 |
| `TRAIN` | обучение распознавания, новая версия модели | FR-061, FR-062, FR-065 |
| `HASH` | подсчёт `sha256` исходного файла эпизода | FR-089, FR-090 |

Вида `ASSEMBLE` **не существует**: сборка подборки выполняется на машине
пользователя (ADR-0009), и на сервере ей нечем заняться. Исполнитель заданий
есть **только у админского бэкенда**; у публичного его нет вовсе
(`research.md` Т-20) — это структурная гарантия того, что собрать подборку за
пользователя нечем (FR-085).

## 3. Обязательные правила для любого вида

### 3.1 Проверка кода возврата — всегда

1. Внешняя программа запускается так, чтобы её **стандартный вывод и вывод
   ошибок объединялись** в один поток: иначе ошибка может остаться
   незамеченной.
2. Код завершения проверяется **всегда**, без исключений и без «успеха по
   умолчанию».
3. Ненулевой код завершения переводит задание в `ERROR` и записывает текст
   ошибки в задание. Текст ошибки — это то, что оператор увидит, поэтому он
   должен быть читаемым, а не «процесс завершился с кодом 1».
4. Задание не может быть помечено `DONE`, если хотя бы одна внешняя программа
   не была запущена или вернула ненулевой код. Это проверяется ограничением
   на уровне хранилища, а не только кодом.

### 3.2 Атомарная запись артефакта

1. Артефакт пишется по **временному** ключу.
2. После нулевого кода завершения и проверки результата временный объект
   переносится на окончательный ключ.
3. Регистрация артефакта в состоянии `READY` выполняется **после** переноса.
4. **Незавершённый файл не считается готовым**: артефакт в состоянии
   `WRITING` не выдаётся ни в интерфейс, ни в сборку, ни в проверку
   готовности эпизода.
5. При сбое временный объект удаляется, регистрация переходит в `FAILED`.

### 3.3 Идемпотентность и версионирование результата

1. Каждое задание несёт **хеш входных параметров**: версию алгоритма, набор
   порогов и настроек эпизода, состав входа.
2. Воркер **не выводит** результат из факта существования файла: «файл есть»
   не означает «работа выполнена». Проверяется регистрация артефакта в
   состоянии `READY` для того же хеша параметров.
3. Смена версии алгоритма или набора параметров **помечает старые результаты
   устаревшими**, но **не удаляет их** и **не запускает пересчёт
   автоматически**: автоматический пересчёт уничтожил бы ручные правки
   оператора (SC-006).
4. Пересчёт запускает оператор явно.

### 3.4 Разделение сырого и ручного

1. Каждый прогон анализа создаёт **собственные** сырые границы. Сырой результат
   не перезаписывается.
2. Ручная правка меняет **рабочую** границу и её признак происхождения; сырой
   результат остаётся для сравнения.
3. Лицо, нарисованное оператором, **не удаляется** повторным анализом: анализ
   добавляет найденное и обновляет автоматические лица, но не трогает лиц
   с происхождением «сделано человеком».
4. Граница, отменённая оператором, сохраняет признак отмены при повторном
   анализе: решение человека — это тоже решение, а не отсутствие данных.

### 3.5 Прогресс и прерывание

1. Прогресс пишется в задание периодически, а не в конце: интерфейс должен
   видеть движение.
2. Прогресс задаётся явно: для проходов ffmpeg — поток прогресса ffmpeg, для
   собственных вычислений — счётчик обработанных единиц из известного общего
   объёма.
3. Прерванное задание возвращается в `WAITING` с **сохранённым** прогрессом;
   работа не начинается заново молча.
4. Порог перехода в `ERROR` не применяется «по таймеру»: долгая работа — это
   нормально, ошибка — это ненулевой код или исключение.

## 4. Параллелизм

1. Задания, требующие GPU, выполняются **строго по одному**: видеокарта одна.
2. Задания на CPU выполняются параллельно с ограничением по числу ядер.
3. Значения ограничений — **параметры развёртывания**, а не константы кода
   (Р-13); подбираются замером (`research.md` М-05).
4. Задание `TRAIN` не занимает GPU: обучение линейного классификатора на
   десятках–сотнях эталонов — работа на CPU.

## 4.1. Те же правила на машине пользователя

Воркер на машине пользователя — не контейнер SYP и не часть очереди, но
правила этого контракта к нему **применяются**:

1. **Проверка кода возврата — всегда**, без исключений. Упавший `ffmpeg` даёт
   ошибку в журнале и ненулевой код возврата воркера, а не «готово». В старом
   проекте не проверял код возврата ни один из двенадцати вызовов ffmpeg — на
   машине пользоваента повторение этого дефекта означало бы, что битый файл
   выдаётся за собранную подборку.
2. **Атомарная запись результата**: файл появляется под окончательным именем
   только целиком.
3. **Разделение сырого и ручного** — здесь про границы сценария: воркер
   **не правит** границы, заданные сценарием, и не «улучшает» их; округление до
   ключевого кадра — зафиксированное решение, а не точка для вмешательства.
4. **Идемпотентность по входам**: сверка `sha256` кэшируется по паре «размер +
   время изменения»; повторный запуск того же сценария не читает диск заново,
   но и не пропускает проверку при изменённом файле.

## 6. Проверяемые свойства этого контракта

Тестами закрываются следующие утверждения — каждое проверяемо, каждое
соответствует требованию:

1. Внешняя программа, завершившаяся с ненулевым кодом, приводит задание в
   `ERROR` с текстом ошибки, а не в `DONE` (FR-004, FR-092, SC-005).
2. Прерванный на середине процесс не оставляет артефакта в состоянии `READY`
   (FR-091).
3. Задание с тем же хешем параметров не выполняется повторно, а задание с
   изменившимся хешем — выполняется (Р-10).
4. Повторный анализ не удаляет нарисованные оператором лица и не снимает
   признак ручной границы (FR-014, SC-006).
5. Смена порога в настройках помечает результат устаревшим, но не удаляет его
   (FR-090).
6. Прерванное задание возвращается в очередь с сохранённым прогрессом
   (FR-003).
7. Сценарий не выдаётся при несовместимых эпизодах (FR-087) и при отсутствии
   актуальной суммы `sha256` (FR-089).
8. Прерванный подсчёт суммы не оставляет запись в состоянии `DONE`, и у эпизода не
   может оказаться двух актуальных сумм (FR-089, FR-090).
9. На машине пользователя: сценарий с неверной подписью **не выполняется**, а
   сценарий с несовпавшей суммой источника **не начинает нарезку**
   (FR-089c, FR-089, SC-012). Первое верно для всех запусков, кроме первого
   на машине: там проверка подписи ослаблена осознанно (FR-089h), ключ
   получается с сервера, ослабление записывается в журнал и со второго запуска
   не повторяется. Суммы источников проверяются всегда, без исключений.
