# Контракт: формат сценария сборки и его выполнение

**Feature**: 001-first-vertical-slice
**Нормативная основа**: ADR-0009, ADR-0006, ADR-0001, constitution IV,
`research.md` Т-23…Т-30.
**Требования**: FR-080…FR-089e; критерии SC-004, SC-008, SC-010, SC-011,
SC-012.

Этот контракт — граница между сервером и машиной пользователя. Сервер по нему
**отдаёт** сценарий; машина пользователя по нему его **выполняет**. Всё, что
не описано здесь, воркером не делается.

## 1. Что пересекает границу

| Объект | Направление | Что это |
|---|---|---|
| Файл сценария | сервер → пользователь | текст в канонической форме, подписанный |
| Открытый ключ | сервер → пользователь | чем проверять подпись |
| Сценарий сборки | машина пользователя → сервер | **ничего**: отчёта о выполнении сервер не получает |
| Готовый видеофайл | — | **никогда**: ни на сервер, ни в сеть (FR-088, FR-089e) |
| Отчёт о выполнении | остаётся у пользователя | рядом с готовым файлом (FR-083, FR-089e) |

**Доставка ручная.** Пользователь скачивает файл сценария браузером и сам кладёт
его в папку сценариев (решение владельца 2026-10-02). Автоматическая доставка
в контракт не входит и в первом срезе не проектируется.

## 2. Формат файла сценария

JSON в **канонической форме**. Канонизация — не украшение: подпись существует
только вместе с определением «что именно подписано».

### 2.1 Правила канонизации

1. Порядок полей фиксирован и совпадает с порядком в этом документе.
2. Отступов нет; между элементами — одиночный перевод строки `LF`.
3. Без BOM, кодировка UTF-8.
4. Числа — целые, без дробной части, без ведущих нулей; порядок ключей
   объектов, которые являются массивами, сохраняется.
5. Никаких пустых полей: отсутствующее необязательное значение **не пишется**,
   а не пишется как `null`.
6. Переводы строк внутри строковых значений экранируются единообразно.

Проверяемое свойство: **одни и те же данные, выданные дважды, дают побайтово
одинаковый файл**. Иначе проверка подписи превращается в лотерею.

### 2.2 Структура

```json
{
  "schemaVersion": 1,
  "serialId": 4,
  "serialName": "Игры Престолов",
  "recipeId": 55,
  "recipeName": "Джейми — выходы",
  "createdAt": "2026-10-02T12:41:07Z",
  "rootLayout": "SERIAL_TREE",
  "audioTrackCount": 1,
  "expectedDurationMs": 412000,
  "expectedFrameCount": 9876,
  "items": [
    {
      "ordinal": 1,
      "sceneId": 1,
      "sceneTitle": "Джейми у ворот",
      "location": "Лагерь Джейми",
      "persons": ["Джейми Ланистер"],
      "seriesId": 7,
      "seriesName": "GOT.S01E01",
      "relativePath": "GOT.S01/GOT.S01E01.BDRip.1080p.mkv",
      "sourceSha256": "3f786850e387550fdab836ed7e6dc881de23001b1a2c3d4e5f60718293a4b5c6d",
      "firstFrame": 1200,
      "lastFrame": 1455,
      "cutFirstFrame": 1188,
      "cutLastFrame": 1460
    }
  ]
}
```

### 2.3 Значения полей

| Поле | Смысл | Правило |
|---|---|---|
| `schemaVersion` | версия формата | воркер отвергает версию новее той, которую понимает, и говорит об этом прямо |
| `rootLayout` | как устроены пути | `SERIAL_TREE` — пути относительно корня сериала (FR-089a) |
| `relativePath` | путь к файлу серии | **не абсолютный**, не содержит `..` нигде; указывает на файл внутри копии сериала |
| `sourceSha256` | эталонная сумма файла | 64 шестнадцатеричных символа в нижнем регистре (FR-089) |
| `firstFrame`, `lastFrame` | расчётные границы фрагмента | по размеченному плану; номер кадра — единственный источник правды (ADR-0001) |
| `cutFirstFrame`, `cutLastFrame` | фактические границы фрагмента | `cutFirstFrame <= firstFrame`, `cutLastFrame >= lastFrame`; начало — ближайший ключевой кадр не позже начала плана (ADR-0006) |
| `sceneTitle`, `location`, `persons` | снимок данных сцены | нужны локальному показу; сайт в показе не участвует (FR-089d) |
| `expectedDurationMs`, `expectedFrameCount` | расчёт по сумме фактических границ | FR-083 |

**Сценарий самодостаточен.** Всё, что нужно для показа и для сборки, лежит в
файле: сервер в момент показа не нужен и не опрашивается.

**Сценарий — данные, а не программа.** Воркер не выполняет файл: он разбирает
его как JSON и выполняет собственную логику. Образец воркера Karaoke выполняет
найденный `.sh` напрямую (`/sm-karaoke/system/karaoke_watcher.sh`); здесь так
делать нельзя, потому что файл приходит из интернеса и проходит через браузер и
файловую систему пользователя.

## 3. Подпись

| Что | Значение |
|---|---|
| Алгоритм | Ed25519 |
| Что подписывается | **канонические байты файла сценария целиком** |
| Как хранится подпись | отдельно: `GET /api/recipes/{recipeId}/signature`, поле `signature`, base64 |
| Идентификатор ключа | `signingKeyId`, входит в сценарий |
| Сумма содержимого | `contentSha256` — `sha256` канонических байтов, хранится рядом с подписью |

Подпись хранится **вне** подписываемого файла: подписываемые байты и подпись
разделены намеренно, иначе пришлось бы подписывать «файл с местом для
подписи», и определение расплылось бы.

Закрытый ключ — только в переменной окружения развёртывания, в репозитории его
нет (constitution VIII). Смена ключа даёт новый `signingKeyId`; ранее выданные
сценарии остаются проверяемыми по прежнему ключу, пока он в списке доверенных.

## 4. Что делает воркер

Воркер — программа на машине пользователя. Он наблюдает каталог сценариев,
обрабатывает по одному файлу за проход, ведёт журнал. Решения по устройству —
`research.md` Т-24.

### 4.1 Порядок действий

Порядок **не переставляется**: каждая проверка дешевле следующего шага, а
проверка после начала работы стоит пользователю часа ожидания впустую.

1. **Проверить среду.** Наличие `ffmpeg`, `ffprobe`, `openssl`, прав на каталог
   результата и на каталог сценариев. При отсутствии — внятное объяснение, что
   установить; сценарий не тронут.
2. **Прочитать файл и проверить подпись.** Подпись сверяется с каноническими
   байтами файла. При несовпадении — **не выполнять**, назвать файл, оставить
   его на месте.
3. **Проверить версию формата.** Незнакомая версия — отказ с текстом, а не
   попытка разобрать незнакомую структуру.
4. **Проверить структуру каталогов.** Для каждого `relativePath` файл должен
   существовать под корнем сериала. Нет — отказ с указанием ожидаемого пути.
5. **Проверить сериал.** Сценарий для другого сериала — отказ с указанием
   обоих. Сценарий, положенный не в тот каталог, — тоже.
6. **Сверить `sha256` всех файлов.** Сверка всех файлов **до** первой нарезки.
   Результат кэшируется по паре «размер + время изменения». При несовпадении —
   **отказ с названием несовпавшего файла**, нарезка не начинается.
7. **Нарезать фрагменты** по `cutFirstFrame`/`cutLastFrame` потоковым
   копированием. Проверять код возврата каждой внешней программы.
8. **Склеить** конкатенацией потоковым копированием, одна аудиодорожка, выход
   MP4.
9. **Записать результат атомарно** под окончательным именем. Прерванный файл не
   остаётся под окончательным именем (FR-091).
10. **Измерить фактические длительность и число кадров**, записать отчёт о
    выполнении рядом с файлом (FR-083).
11. **Встроить главы** потоковым копированием и положить локальную страницу со
    списком сцен (FR-089d).
12. **Запустить показ** по умолчанию; при следующих стартах воркера показ сам не
    поднимается.
13. **Перенести обработанный сценарий** в каталог обработанных, а не удалить
    молча: после сбоя пользователь должен иметь возможность разобраться.

### 4.2 Отказ до работы

| Проверка | Отказ выглядит так |
|---|---|
| Нет `ffmpeg` | «установите ffmpeg», сценарий не тронут |
| Подпись не сходится | «подпись не сходится, сценарий не выполнен», файл остаётся |
| Незнакомая версия формата | «сценарий версии N, воркер понимает до M» |
| Нет файла | «ожидался путь X, найдено Y» |
| Не совпала сумма | «не совпала сумма файла X», нарезка не началась |
| Чужой сериал | «сценарий для сериала A, в каталоге B» |

### 4.3 Чего воркер не делает

- не выполняет файл сценария как программу;
- не обращается к серверу во время работы и после неё;
- не загружает ни готовый файл, ни отчёт на сайт (FR-089e);
- не изменяет исходные файлы;
- не запускает показ автоматически при каждом старте;
- не «чинит» округление перекодированием (ADR-0006).

## 5. Формат отчёта о выполнении

Кладётся рядом с готовым файлом, имя — `<имя файла>.syp-result.json`. Сервер его
**не получает** (FR-089e).

```json
{
  "schemaVersion": 1,
  "recipeId": 55,
  "recipeContentSha256": "9f2c…",
  "finishedAt": "2026-10-02T13:02:44Z",
  "state": "DONE",
  "outputFile": "Джейми — выходы.mp4",
  "expected": {"durationMs": 412000, "frameCount": 9876},
  "actual": {"durationMs": 416583, "frameCount": 9960},
  "difference": {
    "durationMs": 4583,
    "frameCount": 84,
    "cause": "округление границ до ключевых кадров при склейке без перекодирования"
  },
  "sources": [
    {"relativePath": "GOT.S01/GOT.S01E01.BDRip.1080p.mkv", "sha256Checked": true}
  ],
  "items": [
    {"ordinal": 1, "expectedFrames": 273, "actualFrames": 273}
  ]
}
```

При неудаче `state` равен `ERROR`, `errorText` обязателен, а `actual` может
отсутствовать. **Расхождение с расчётом — не дефект**: это ожидаемое следствие
склейки без перекодирования (ADR-0006, FR-082), и оно показывается, а не
прячется.

## 6. Проверяемые свойства этого контракта

Каждое утверждение проверяемо и соответствует требованию:

1. Сценарий с изменённым байтом **не выполняется вовсе**, файл остаётся на
   месте (FR-089c, SC-012).
2. Подмена одного байта **после** подписания обнаруживается: подпись сверяется с
   каноническими байтами файла, а не с содержимым, разобранным «как получится»
   (FR-089c).
3. Сценарий с несовпавшей суммой источника **не начинает нарезку** и называет
   файл (FR-089, SC-012).
4. Сценарий, положенный в папку при отсутствующем `ffmpeg`, **не меняет
   состояния**: в журнале — внятное объяснение (ADR-0009, последствие 7).
5. Сценарий, уводящий за пределы копии сериала, отвергается проверкой пути, а
   не приводит к чтению чужого файла (FR-089a).
6. Прерванная на середине сборка **не оставляет** файла под окончательным именем
   (FR-091).
7. Упавший `ffmpeg` даёт ошибку в журнале и ненулевой код возврата воркера, а не
   «готово» (constitution IV.2, SC-005).
8. Повторная выдача тех же данных даёт **побайтово те же** канонические байты
   (основание проверки подписи).
9. Готовый файл и отчёт о выполнении остаются на машине пользователя; на сервере
   их нет (FR-089e, SC-011).
10. Список сцен в локальном показе содержит название, персонажей и место
    действия каждого фрагмента и работает без обращения к серверу (FR-089d).
