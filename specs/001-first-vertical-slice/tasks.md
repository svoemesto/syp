# Tasks: Первый сквозной вертикальный срез SYP (схема «рецепт»)

**Input**: документы фичи из `specs/001-first-vertical-slice/`
**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md
**Tests**: тестовые задачи включены — контракты `job-queue.md` и
`recipe-format.md` перечисляют проверяемые свойства, и каждое из них требует
теста (`AGENTS.md` § Tier-1 «Hard Gate: Living docs SSoT», constitution VI).

**Organization**: фазы идут в порядке плана (15 фаз, 0…14) — этот порядок
обязателен, потому что каждая следующая фаза опирается на результат
предыдущей. Внутри порядка фазы сгруппированы по пользовательским историям
спецификации: одна история может занимать несколько фаз (US1 — фазы 3…9
плана).

**Этот список не меняет ни одного FR и ни одного SC.** Спецификация — контракт
(constitution IX.4). Здесь 66 FR и 12 SC закрываются задачами, а не правкой
спеки. Расхождения, найденные при разбиении, вынесены в раздел
«Расхождения, требующие решения владельца».

**Цель**: проект собирается, шесть контейнеров поднимаются, проверки

**Проверка фазы**: `bash deploy/do.sh status` показывает шесть контейнеров;

- [ ] T188 **Декодер не должен висеть незамеченным.** Детекция лиц стояла трижды подряд в состоянии «идёт работа» при живом декодере, который не отдавал ни кадра, ни байта: состояние задания утверждало, что работа идёт, и ответ API говорил то же. Видно это только сверкой трёх фактов — состояние задания, изменение числа найденных лиц и список процессов. Требование: чтение кадров идёт с ограничением времени, и если декодер не отдал кадр за разумный срок, задание переходит в `ERROR` с указанием номера кадра и вывода программы; зависший декодер обязан быть уничтожен. Отдельно: недобранный кадр по-прежнему обязан давать отказ, а не молчание — при переносе чтения на поток с ожиданием это легко потерять, и существующая проверка на усечённый кадр обязана продолжать это ловить. Проверка: зависший декодер даёт отказ за минуты, а не зависание; проверка на усечённый кадр падает вместе с этой правкой.

- [x] T188 **Задание не должно висеть после смерти исполнителя.** Задание детекции лиц пережило пересоздание контейнера: процесс детектора умер вместе с контейнером, а задание осталось в состоянии `WORKING` навсегда — полтора часа без движения, при живом на вид API. Требование: при старте воркер обязан находить задания в состояниях `CREATING`/`WORKING`, чей исполнитель не существует, и переводить их в `ERROR` с указанием причины; либо хранить признак живости исполнителя в задании и проверять его по таймеру. Проверка: задание, оставленное в `WORKING` при отсутствии процесса, должно быть обнаружено за минуту, а не висеть. Там же: порция про устойчивость к пересозданию контейнера вообще — перезапуск разрешён владельцем, и очередь обязана это переживать.

# Dependencies & Execution Order

## Phase Dependencies

```
Phase 1  Каркас
   ↓
Phase 2  Очередь, внешние программы, артефакты, ключи   ← блокирует всё остальное
   ↓
Phase 3  Приём эпизода
   ↓
Phase 4  Справочник сумм
   ↓
Phase 5  Анализ структуры
   ↓
Phase 6  Лица
   ↓
Phase 7  Размер плана
   ↓
Phase 8  Ручная доводка
   ↓
Phase 9  Место действия
   ↓
Phase 10 Обучение (US2)
   ↓
Phase 11 Фильтры (US3)
   ↓
Phase 12 Выдача сценария
   ↓
Phase 13 Публичная часть
   ↓
Phase 14 Воркер
   ↓
Phase 15 Локальный показ
   ↓
Phase 16 Приёмка
```

Порядок **не переставляется**. Нарушение порядка означает переделку: анализ
без карты ключевых кадров не даст фактических границ фрагмента, сценарий без
актуальной суммы нельзя выдать, а воркер без подписи бесполезен.

## User Story Dependencies

- **US1 (P1)** — фазы 3…9. Самостоятельный вертикальный срез: эпизод
  размечена и доводится вручную. Закрывает SC-001, SC-002, SC-003, SC-006.
  MVP среза.
- **US2 (P2)** — фаза 10. Начинается после фазы 6: нужны эмбеддинги и эталоны.
  Закрывает SC-009. Без US1 история не тестируется.
- **US3 (P2)** — фаза 11. Начинается после фаз 5, 6, 9: фильтр ссылается на
  персон, места действия и размеры плана. Закрывает SC-007.
- **US4 (P3)** — фазы 12…15. Начинается после US3: пользователь применяет
  сохранённый фильтр. Закрывает SC-004, SC-008, SC-010, SC-011, SC-012.

  провалить, считается отсутствующим.
- Замер выполняется **до** того, как его число попадёт в настройки фильма.

# Implementation Strategy

## MVP First (User Story 1)

1. Завершить Phase 1 (каркас).
2. Завершить Phase 2 (очередь) — **критично, блокирует всё остальное**.
3. Завершить фазы 3…9 плана — это US1 целиком.
4. **Остановиться и проверить**: эпизод `GOT.S01E01` размечена, ни одна ручная
   правка не потеряна, границы сверены с эталоном старого проекта.
5. Это уже ценность: инвентаризация инвентаризирована, дальше — обучение,
   фильтры и выдача сценария.

## Incremental Delivery

1. Phase 1 + Phase 2 → фундамент готов.
2. Фазы 3…9 → US1 → проверка → демонстрация оператору (MVP).
3. Фаза 10 → US2 → проверка → откат модели работает.
4. Фаза 11 → US3 → проверка → фильтр применяется одним действием.
5. Фазы 12…15 → US4 → проверка → пользователь получает файл у себя.
6. Phase 16 → приёмка среза.

## Длина среза

Фаза 5, фаза 6 и фаза 8 — самые длинные по времени: каждая включает прогон
полного эпизода (88 643 кадра). Это не параллелится между собой — задания
занимают видеокарту и диск архива.

# Расхождения, требующие решения владельца

Ни одно из расхождений не «чинится» в этом файле: спецификация — контракт

Пересмотрено 2026-10-03 по итогам `analysis.md`: три пункта описывали
состояние, которого уже нет, и сняты; вместо них внесены реальные вопросы.

1. **SC-004 и объём сверки сумм.** Подборка из десяти эпизодов — это 56 ГБ
   чтения. Если М-12 покажет, что критерий 5 минут не выполняется, ходы:

   самого критерия. Первые два — технические (T148), третий меняет
   спецификацию и может быть сделан только словом владельца. Задача T161
   фиксирует измерение, но не предрешает решение.

2. ~~**Место создания и подписи сценария сборки.**~~ **ЗАКРЫТО решением
   владельца 2026-10-03, ADR-0014.** Противоречие, описанное ранее (ADR-0009 и
   `contracts/public-api.md` отдавали выдачу публичной части, а
