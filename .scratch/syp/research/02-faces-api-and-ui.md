## A. Лица и персонажи

### A.1. Полный конвейер

```
кадры (jpg %06d)  ──frames.json──►  detect_faces_in_folder.py
                                       │ Caffe SSD Res10 300x300  (bbox + confidence)
                                       │ OpenFace nn4.small2       (128-мерный вектор)
                                       ├─► folderFacesFull/<short>_frame_%06d_face_%02d.jpg
                                       └─► folderFramesFull/faces.json
                                              │
faces.json ──► CreateFaces.kt ──► tbl_faces (vector = TEXT "v|v|v|…", person = UNDEFINDED)
                                              │
tbl_faces WHERE is_example = true ──► embeddings.json ──► train_model_json.py
                                              │                └─► recognizer.pickle + le.pickle

faces.json (только personType == 'UNDEFINDED') ──► recognize_faces.py
                                              └─► faces.json (personRecognizedName, recognizeProbability)

```

### A.6. Хранение и «не лицо»

**Формат хранения векторов** — `@Lob`-строка с разделителем `|`
([03:350–369]), не 128 колонок и не BLOB:

```kotlin
@Column(name = "vector") var vectorText: String = "0.0"
var vector: DoubleArray
    get() = vectorText.split("\\|".toRegex())...
    set(value) { vectorText = value.joinToString(separator = "|") }
```

Сравнение при обновлении — `contentEquals` по `DoubleArray`, покомпонентно,
без epsilon ([03:375]). Последствие из техдолга: **нельзя сравнивать и
фильтровать векторы в SQL**, нужен полный `SELECT *` ([03:923]).

Поля `tbl_faces`: `face_number_in_frame`, `frame_number`,
`person_recognized_name`, `recognize_probability`, `start_x/start_y/end_x/end_y`,
`is_example`, `is_manual`, `vector` + связи `@ManyToOne` на `file` и `person`
([03:377–383]).

**Естественный ключ лица** — тройка `(fileId, frameNumber, faceNumberInFrame)`
([03:436]). Известный баг: при `frameId != 0` код ищет
`findById(faceExtJson.frameId)` вместо `faceId` ([03:428–434], [03:922]).

**Фильтр «не лицо»** — единственный, и он на стороне Kotlin, в
`FaceController.createOrUpdate`: по пропорциям bbox

```kotlin
val d = if (w > h) w/h.toDouble() else h/w.toDouble()
if (d > 4) face.person = nonPerson.person   // слишком вытянутый bbox → NONPERSON
```

([03:438–445]). То есть «не лицо» = аспект bbox > 4. Никаких других признаков
(одежда, отсутствие глаз, глубина) не используется.

**Типы персон** — `PersonType`: `PERSON`, `UNDEFINDED`, `NONPERSON`, `EXTRAS`
([04:450–454], [04:756]). Три последних — плейсхолдеры, доступные оператору через
контекстное меню.

**Какие кадры вообще анализируются** — адаптивный шаг по длине плана
([03:447–463]):

```
длина плана < 15 кадров  → шаг 3
< 30                      → шаг 5
< 60                      → шаг 10
иначе                    → шаг 20
+ всегда последний кадр плана
```

Это ключевой факт для SYP: **лица детектируются не в каждом кадре**, а на
выборочных кадрах с шагом, зависящим от длины плана. Имя файла кадра —
`%06d`, шаблон `${shortName}_frame_%06d.jpg` ([03:460–463]).

### B.2. Что фактически является «API»

По [03:45–52] — ровно три механизма:

1. **Внутрипроцессный Kotlin/Java API** — статические методы вида
   `ProjectController.getProjectExt(id)`, `FaceController.getListFacesExt(...)`.
   Полный перечень всех 17 контроллеров с их методами — [03:487–627]
   (например, `SceneController.getOrCreate` — самая нетривиальная логика:
   поиск пересекающихся сцен и их расщепление на 1/2/3 части либо удаление,
   [03:545–553]).
2. **JSON-протокол обмена с Python** (Gson ↔ `json`) — **единственный реальный
   «сетевой» интерфейс приложения**. Файлы: `frames.json` (вход детекции,
   [03:173–186]), `faces.json` (выход детекции + вход и выход распознавания —
   один и тот же файл перезаписывается, [03:234–235], [03:279]),
   `embeddings.json` (обучение, [03:294]).
3. **JavaFX `ObservableList`** — «выдача» данных в UI (`table.items = list`,
   [03:656]).

Дополнительно: **CDF** («Computer-Dependent File») — пути к рабочим папкам
зависят от машины, поэтому хранятся как пара «объект + computer_id», где
`computer_id` = `hashCode()` от `OS.manufacturer # CPU.processorID #
CPU.identifier # logicalProcessorCount` (OSHI) ([03:629–637]). Плюс временные
таблицы `tbl_shot_tmp_cdf` / `tbl_shot_tmp2_cdf` — «одноразовые» списки
выборок в пределах текущей машины ([03:533–540], [03:636–637]).

Формат «отдачи» наружу — три разных ([03:639–658]):

- **JSON через Gson**: `FaceExt` — гибрид: transient-поля (`face`, `fileExt`,
  `personExt`) + поля-транзиенты с `@SerializedName` (`toSerialize*`), т.е.
  Gson сериализует прокси-поля под «настоящими» именами ([03:644–655]);
- **`ObservableList<…Ext>`** в UI;
- **Entity → Ext-обёртки** наружу (Spring Data отдаёт `Iterable<Entity>`).

### B.4. `loadlists` — отложенная загрузка как конвейер

13 классов в `threads/loadlists/` ([03:680–690]). Единый шаблон, 13 копий
одного класса ([03:692–730]):

- фоновый `Thread`, запрос к БД и построение объектов вне FX-потока;
- добавление каждого элемента в `ObservableList` через `Platform.runLater` —
  список наполняется **инкрементально**, пользователь видит прогресс
  ([03:733–738]);
- кооперативная отмена — единственная точка `if (!currentThread().isInterrupted) return`
  ([03:739–741]);
- **согласованность «список ⇄ БД» через флаг**: каждому списку соответствует
  `SimpleBooleanProperty flagIsDone`; UI слушает его, сбрасывает и
  переприсваивает `table.items = list` ([03:742–751]).

Ключевое: loadlists образуют **DAG**, а не набор кнопок —
`кадры → (планы, сцены, события)` ([03:753–784]). Причина прямо в коде:
`fileExt.framesExt.first { it.frame.frameNumber == shot.firstFrameNumber }` —
если кадры не загружены, `NoSuchElementException`. То есть `flagIsDone` — это
join-точка асинхронного конвейера ([03:778–784]).

И потоки обработки тоже грузят списки перед генерацией видео
([03:786–793]).

### B.5. `updatelists` — инвалидация ленивых кэшей

Всего 2 класса: `UpdateListFilesExt`, `UpdateListFramesExt` ([03:797–800]).
Список **не перечитывается из БД** — он уже в памяти; обновляются только ленивые
вычисляемые свойства `Ext`-объектов, кэшируемые в `_xxx`-полях
([03:802–805], [03:806–835]).

Пример ленивого кэша — `FaceExt.previewSmall` ([03:849–870]): если файла
превью нет, он вырезается из полного кадра, помечается треугольником по
`isExample`/`isManual`, сохраняется и кэшируется; `resetPreviewSmall()`
сбрасывает кэш явно ([03:871]).

**«Инкрементальность» двойная** ([03:873–881]): (а) не перечитывать БД, а
пересчитать вычисляемые свойства; (б) проверять наличие результата **по файловой
системе** через regex имени файла, а не по флагу в БД:

```kotlin
val faceFilenameRegex = Regex("^${fileNameRegexp}_frame_\\d{6}_face_\\d{2}\\.jpg$")
return (IOFile(fld).listFiles { _, name -> name.contains(faceFilenameRegex) }?.size ?: 0) > 0
```

Запуск: `UpdateListFramesExt` стартует сразу после `LoadListFramesExt` из
колбэка loadlist; `UpdateListFilesExt` — по кнопке обновления панели файлов
([03:883–887]).

### B.6. Почему HTTP API не было

**Прямого объяснения в отчётах нет.** Следующие из фактов причины (это моя
реконструкция, а не цитата):

- приложение — однопользовательское десктопное JavaFX-приложение, UI и логика
  в одном процессе, прямой вызов статического метода дешевле HTTP-запроса
  ([03:41–52], [04:687–716]);
- данные локальны, пути на диске зависят от машины (CDF, [03:629–637]) —
  серверной модели доступа не было;
- единственный внешний исполнитель (Python+OpenCV) запускается локально через
  `ProcessBuilder` и обменивается файлами JSON, а не сокетом
  ([03:109–141], [03:173–186]);
- отдельный сервис-процесс потребовал бы отдельной модели транзакций, а
  `@Transactional` на FX-контроллерах и так **не работает** (контроллеры не
  Spring-бины) ([04:394], [04:709]).

### C.2. Пользовательский сценарий по шагам

**Шаг 5. Редактирование** ([04:426–479]) — подробно в C.4.

### C.3. Матрица кадров и матрица лиц

**Константы размеров** ([04:566–578]):

```
FULL_FRAME_W/H      = 1920 / 1080
MEDIUM_FRAME_W/H    = 720  / 400
PREVIEW_FRAME_W/H   = 135  / 75
PREVIEW_FACE_W/H    = 75   / 75      (квадрат)
PREVIEW_FACE_EXPAND_FACTOR = 1.4 ; PREVIEW_FACE_CROPPING = false
```

**Матрица кадров** (`MatrixPageFrames` / `MatrixFrame`) — вкладка «Frames»
([04:580–600]). Разбиение на страницы:

```
countColumns = ((paneW - ((picW+2)*2 + 20)) / (picW+2)).toInt()
countRows    = ((paneH - ((picH+2)*2 + 20)) / (picH+2)).toInt()
```

**Где граница плана разрывает строку** — ключевая механика ([04:589]):
`isFinalFind` (кадр — окончательная граница плана) **разрывает строку**, а не
просто занимает ячейку: если следующий кадр `isFinalFind`, делается
`currentRow++` вместо `currentColumn++`.

**Дубликаты на стыке страниц** ([04:589]): при переходе на новую страницу
крайние «половинки» плана дублируются — `omegaMatrixFrame` (кадр перед разрывом,
с координатой последней ячейки предыдущей страницы + 1) и `alfaMatrixFrame`
(кадр после разрыва, `column=1,row=0` либо `column=0,row=1` — за левым/над
верхним краем). **Один и тот же план виден на стыке двух страниц** — оператор
видит, что шот продолжается.

Отрисовка — переиспользуемые `Label` из `frameExt.labelSmall`,
позиционируемые вручную:

```kotlin
lbl.translateX = 10 + matrixFrame.column * (Main.PREVIEW_FRAME_W + 2)
lbl.translateY = 10 + matrixFrame.row    * (Main.PREVIEW_FRAME_H + 2)
```

([04:592–598]). Важно: если кадр «интересный» (граница плана у него или у
соседей, он I-кадр, или в кадре есть лица) — рисуется JPEG 135×75, иначе ячейка
пустая (Pane чёрный). Это «визуализация только релевантных кадров» —
экономия места ([04:600]).

**Матрица лиц** (`MatrixPageFaces` / `MatrixFace`) — вкладка «Persons»
([04:627–646]). Ячейка 75×75 квадратная; **логики разрыва по `isFinalFind` нет** —
лица идут подряд по списку; на стыке страниц добавляется только **один**
дубликат крайнего лица с `column=0, row=1`.

`FaceExt.previewSmall` лениво ([04:637]): если файла превью нет — вырезает область
из **полного** кадра с `PREVIEW_FACE_EXPAND_FACTOR = 1.4`, помечает `isExample`
зелёным треугольником, `isManual` красным, сохраняет в
`folderFacesPreview/<short>_frame_%06d_face_%02d.jpg` и кэширует. **Файл превью —
это кэш, который можно удалить, и он пересоздастся.**

Внутри ячейки лица — именно лицо, а не фото персоны; фото персоны живёт в других
местах (`labelPersonSmall`, `PersonExt.labelSmall` 135×75 с именем подчёркиванием,
`PersonExt.labelMedium` 720×400) ([04:640–644]).

Ресайз ([04:666–668]): на изменение размера `pane` пересчитываются только
колонки/строки, и **только если число реально изменилось** — пересобираются
страницы, восстанавливается текущий кадр/лицо, перерисовывается страница.
Позиция оператора не теряется.

### C.4. Цветовая семантика оверлеев

**На миниатюрах кадра** ([04:602–615]):

| Условие | Что видно |
|---|---|
| в кадре есть лица | **синий** треугольник в правом верхнем углу |
| `frame.isIFrame` | **голубая** буква `I` по центру, MONOSPACED BOLD 26, opacity 0.9 |
| `frame.isFind` (начало плана) | **красная** строка `╚════╝` сверху |
| `frame.isFind && isManualCancel` | **оранжевая** `[` слева, 48pt, opacity 0.2 |
| следующий кадр `isFind` (конец плана) | **красная** строка `╔════╗` снизу |
| следующий `isFind && isManualCancel` | **оранжевая** `]` справа |
| `frame.isManualAdd` | **зелёная** `╚════╝` сверху |
| следующий `isManualAdd` | **зелёная** `╔════╗` снизу |

Семантика одной строкой ([04:615]): **красный = найдено алгоритмом**,
**зелёный = сделано оператором**, **оранжевый = отменено оператором**,
**голубой = I-кадр**, **синий треугольник = есть лица**.

Рамки состояния на `Label` ([04:617–623]): обычная `#0f0f0f`; наведение —
`YELLOW` + `toFront()`; текущий кадр — `RED`; выделено+наведение — `ORANGE`.

**Оверлеи сцен и событий** — через `ShotExt` ([04:648–664]): ячейки `FROM/TO` в
таблицах — это не текст, а `Label` с картинкой. Три копии каждой
(`labelFirst1/2/3`) существуют, потому что JavaFX-нода не может переехать между
таблицами. `previewsFirst` (начало плана): **оранжевая** полоса 10×H слева +
оранжевые прямоугольники 20×10 в углах, если план попадает в **сцену**;
`previewsLast` (конец): **зелёные** полоса справа и прямоугольники в углах, если
план попадает в **событие**. Пересчёт оверлеев — только для шотов,
пересекающихся с затронутым диапазоном (`isPairIntersected()`).

**Оверлеи на крупном кадре** (`FaceController.getOverlayedFrame`) ([03:465–468]):
цвет подписи `YELLOW` (авто), `RED` (isManual), `ORANGE` (выбранное ручное),
`GREEN` (выбранное авто); под чёрным фоном рисуется имя персоны.

Итоговая палитра проекта — 5 смысловых цветов на миниатюре кадра + 2 на
превью плана. Для SYP это готовая, проверенная оператором схема.

### C.5. Экран project-actions: операции и механика

Таблица файлов — **17 колонок-индикаторов** состояния ([04:499–519]):
`PW` preview, `LL` lossless, `FS/FM/FF` кадры 175×35 / 720×400 / 1920×1080,
`AF` кадры проанализированы, `CS` планы созданы, `DF` лица обнаружены,
`CF` лица вырезаны, `CFP` превью лиц, `RF` лица распознаны,
`SCA/SLA/SLN` видео планов, `CC` сконкатенированный файл.

15 чекбоксов операций в порядке FXML ([04:523–543]): `CreatePreview`,
`CreateLossless`, `CreateFramesSmall/Medium/Full`, `AnalyzeFrames`,
`CreateShots`, `DetectFaces`, `CreateFaces`, `CreateFacesPreview`,
`RecognizeFaces`, `CreateShotsCompressedWithAudio`, `CreateShotsLosslessWithAudio`,
`CreateShotsLosslessWithoutAudio`, `CreateConcat` + глобальный
`RECREATE IF EXISTS` и кнопка `Do actions`.

Зависимости от предусловий отражены **только в тексте чекбоксов**
(`need LL!!!`, `need SLA!!!`), но программно **не проверяются** — если `LL` не
создан, `[SCA]/[SLA]/[SLN]` упадут ([04:545]).

Механика `doActions()` ([04:547–555]):

1. первый проход — для каждого (файл, операция) проверяется
   `чекбокс && (!hasXxx || (hasXxx && RECREATE IF EXISTS))`, считается
   `countActions` — **идемпотентность по умолчанию**;
2. второй проход — создаётся поток с обоими `ProgressBar` и обоими `Label`,
   т.к. ffmpeg- и python-фазы внутри одного действия используют разные
   индикаторы;
3. `RunListThreads(listThreads).start()` — параллельный запуск всего списка.

### C.6. Механики ручной доводки

**а) Границы планов — split/union.** Двойной клик по миниатюре кадра
([04:428–437]):

| Состояние кадра | Действие |
|---|---|
| `isFind` и **не** `isManualCancel` | `isManualCancel = true`, `isFinalFind = false` → `splitOrUnionShots()` |
| `isFind` и `isManualCancel` | отметка снимается, `isFinalFind = true` |
| **не** `isFind` и **не** `isManualAdd` | `isManualAdd = true`, `isFinalFind = true` |
| `isManualAdd` | снимается, `isFinalFind = false` |

`splitOrUnionShots()` ([04:434–437]):

- **split** (кадр внутри шота, `isFinalFind`): `shot.lastFrameNumber = frameNumber - 1`,
  `ShotController.save()`, `ShotController.getOrCreate(file, frameNumber, lastFrameNumber)`
  создаёт второй шот;
- **union** (кадр — начало шота, `!isFinalFind`): предыдущий шот продлевается до
  `shot.lastFrameNumber`, текущий удаляется;
- после любого изменения матрица и списки перестраиваются заново.

**б) Тип плана.** Кнопка в колонке `TYPE` → `ContextMenu` из `ShotTypePerson` с
пиктограммами, выбор → `shot.typePerson` + `resetPreview()` + `tblShots.refresh()`
([04:439]). Значения: `NONE/SGN/OTS/TWO/GRP/MASS` =
`Не определено/Один/Один через плечо/Двое/Трое и более/Очень много`
([01:529–536]).

**в) Создание лица мышью.** В `frame-faces-edit-view.fxml` ([04:271]):
`onMousePressed` запоминает `startX/startY` и заново строит оверлей;

просто рисует мышью прямоугольник вокруг лица — отдельная кнопка «создать» не
обязательна (хотя есть, с англ. текстом на русском экране). Дальше —
`PersonSelectFXController`; сохраняется `isManual = true`,
`faceNumberInFrame = list.size + 1` ([04:461]).

| Пункт меню | Действие |

### C.7. Автосохранение и единый механизм свойств

**Автосохранение** ([04:792]): сохранение происходит **по потере фокуса** поля
(`focusedProperty().addListener`), либо **при закрытии окна**, либо **при смене
выделения**. **Явной кнопки «Сохранить» в приложении нет вообще.**

Конкретные точки:

- главное окно: `setOnCloseRequest` → `saveCurrentFileProperty()`,
  `saveCurrentFilePropertyCdf()`, `saveCurrentFile()`, `saveCurrentProject()` +
  `interrupt()` фонового потока ([04:187]);
- свойства сохраняются по потере фокуса (`PropertyController.save()`) ([04:441]);
- при смене выбранной персоны — сначала `saveCurrentProperty()` +
  `saveCurrentPerson()`, затем перезагрузка свойств ([04:301]);
- пересчёт превью затронутых шотов после удаления событий ([04:472]).

**Единый механизм свойств (EAV)** — сквозная черта ([04:788–792]): все
редактируемые сущности (`Project`, `File`, `Shot`, `Scene`, `Event`, `Person`,
`Track` + CDF-вариант для `Project`/`File`) используют **одни и те же 6 кнопок**
(в начало / вверх / вниз / в конец / добавить / удалить) и пару
«Key = TextField / Value = TextArea». Шаблон кода
повторяется в 6 контроллерах почти дословно. Пункт «Добавить все свойства для
…» есть только у `Project`/`File`/`Person`, но не у `Shot`/`Scene`/`Event`.
В БД это универсальная EAV-таблица, где `parentClass` — имя класса-владельца,
`parentId` — его id ([03:604–608]).

Ключевой приём: `isExample` (эталон) — это **не отдельная сущность и не тег**,
а булев флаг на строке `tbl_faces` ([03:382]), и обучение берёт ровно эти строки
([03:326–327]).

## D. Явные вопросы владельцу, следующие из этих отчётов

1. **Ракурс лица — отдельная задача или вручную?** В legacy нет ни детектора
   позы, ни ключевых точек, ни классификатора ракурса ([A.7]). Формат ответа
   «Джейми Ланистер, крупный план, в профиль» требует либо новой модели
   (head-pose/landmarks на GPU), либо ручной разметки оператором, либо иного
   определения «положения» (только bbox). **Это блокер спецификации сущности
   «персонаж в кадре».**
2. **Что такое «положение» по умолчанию?** Варианты из legacy: только bbox;
   bbox + размер плана (`ShotTypePerson`); bbox + ручной тег из EAV-свойств;
   автоматический ракурс. Нужно решение владельца, что входит в FR.
3. **Детекция лиц — в каждом кадре или с адаптивным шагом?** В legacy шаг
   3/5/10/20 по длине плана ([A.6]) — на 82 834 кадрах серии это в разы
   дешевле, но «в каждом кадре находить персонажей» из задания SYP этого не
   даёт. Подтвердить или отвергнуть наследование шага.
4. **Классификатор — SVM или нейросеть на GPU?** Legacy: SVC linear поверх
   128-мерных OpenFace-векторов, порог 0.3 жёстко зашит ([A.4]). У SYP есть
   RTX 4060 Ti — стоит ли переходить на GPU-эмбеддинги + cosine-классификатор,
   и тогда чей порог и где он конфигурируется (в legacy порог был в коде — это
   дефект).
5. **Хранить лица как строки с разделителем или нормализованно?** Legacy:
   `@Lob` TEXT `"v|v|v|…"` ([A.6]) — нельзя фильтровать в SQL. Для 5,96 млн
   кадров архива это решение влияет на объём БД и на возможность SQL-подобных
   выборок.
6. **Нужен ли публичный HTTP API в SYP вообще?** В legacy HTTP не было
   никогда ([B.1]), потому что это десктоп. В SYP бэкенд обслуживает Vue-фронт —
   API неизбежен. Вопрос: только внутренний `/api` для админки, или ещё и
   «показать сцену» для публичной части?
7. **Ручная доводка — обязательный первый класс или второй?** В legacy это ядро
   продукта ([C.6]). Для SYP: включаем ли редактор границ планов, создание
   лиц мышью и drag&drop в первый вертикальный срез, или сначала только
   автопроцесс + просмотр?
8. **Планы (`Shot`) и сцены (`Scene`) — одна сущность или две?** В legacy это
   разные сущности с разными UI-вкладками и разными цветами оверлеев
   (оранжевый = сцена, зелёный = событие) ([C.4]). В задании SYP фигурирует
   только «сцена». Нужно решение: сцена = план (непрерывный диапазон кадров) или
   сцена = группа планов?
9. **Эталоны (`is_example`) — версии модели.** Каждое обучение перезаписывает
   `recognizer.pickle` / `le.pickle` ([A.5]). Нужна ли история версий модели и
   возможность переобучить и переразметить выборку?
10. **Placeholder-персоны (`UNDEFINDED`/`NONPERSON`/`EXTRAS`) переносим?** Это
    не украшение: `UNDEFINDED` — рабочее состояние «распознано, но не решено»,
    `NONPERSON` — фильтр мусора по аспектному отношению bbox > 4 ([A.6]).
    Оставляем ли четыре типа персон в SYP?

## Итог для карты решений

Развилки, требующие решения владельца. Порядок — по критичности для спецификации.

### Д-1. «Положение персонажа в кадре»: откуда брать ракурс

Legacy-факт: **только bbox**. Детектора позы, ключевых точек и классификатора
ракурса нет ни в одном из прочитанных отчётов ([A.7]); `ShotTypePerson` — это
тип плана по числу людей, а не ракурс лица ([01:529–536]).

Варианты: (а) bbox + ручной тег оператора через существующий EAV-механизм
(дешевле всего, переносится как есть); (б) head-pose-модель на GPU
(InsightFace/6DRepNet-подобная), новая зависимость; (в) только bbox, «ракурс»
в формулировке задания снимается. **Влияет на**: наличие GPU-контейнера,
модель данных сцены, стоимость одного кадра.

### Д-2. Детекция лиц в каждом кадре или с адаптивным шагом

Legacy: шаг 3/5/10/20 по длине плана + всегда последний кадр ([A.6]). Задание
SYP говорит «в каждом кадре находить персонажей». Для 82 834 кадров × 73 серии
(5,96 млн кадров) разница в объёме работы — на порядок. **Нужно решение до
спеки**, потому что от него зависит и схема БД, и тайминг задания очереди.

### Д-3. Формат хранения дескрипторов

Legacy: `@Lob` TEXT с разделителем `|`, невозможно фильтровать в SQL
([A.6]). Для SYP при 5,96 млн кадров это решение масштабируется плохо.
Варианты: Postgres `float4[]`/`vector`/bytea; отдельная таблица с
`(face_id, dim, value)`; внешнее векторное хранилище. Связано с Д-2: меньше
кадров — меньше строк.

### Д-4. Классификатор и где живёт порог

Legacy: sklearn SVC(linear, probability=True), порог **0.3 зашит в Kotlin в
четырёх местах**, аргумент `-c` в Python мёртв ([A.4]). Для SYP: оставлять ли
CPU-SVM или переходить на GPU (у нас RTX 4060 Ti), и — обязательно — вынести
порог в конфигурацию задания, а не в код.

### Д-5. Нужен ли реальный REST API и какой

Legacy HTTP не имеет вообще ([B.1]) — переносить нечего. Для SYP: минимальный
набор эндпоинтов админки (проекты/файлы/кадры/планы/сцены/лица/персоны/задания
очереди) и — отдельно — вопрос, выносится ли наружу «показать результат»
(в SYP-контейнерах публичная часть есть по AGENTS.md, в legacy аналога нет).

### Д-6. Что переносим из UI как ядро

Ручная доводка в legacy — центральная функция ([C.6]): split/union границ,
рисование лица мышью, drag&drop миниатюры на персону, `Set as EXAMPLE`.
Варианты: (а) полный редактор в первом вертикальном срезе; (б) только просмотр
+ базовая правка границ; (в) отложить редактор, сначала автопроцесс.
Определяет объём первого релиза сильно.

### Д-7. План vs сцена — одна сущность или две

Legacy: `Shot` (план, границы кадров) и `Scene` (группа непрерывных планов) —
разные сущности, разные вкладки, разные цвета оверлеев ([C.4], [C.6]). В задании
SYP есть только «сцена». Нужно решение владельца.

### Д-8. Модель обучения: версии и переобучение

Legacy перезаписывает `recognizer.pickle`/`le.pickle` при каждом обучении, эти
файлы лежат в папке проекта ([A.5]). Нужна ли история версий, «переобучить на
расширенной выборке», откат к предыдущей модели. Также: эталон — булев флаг на
`tbl_faces` ([C.7]), а не тег; переносим ли как есть.

### Д-9. Идентичность персоны

Legacy: `uuid` + `nameInRecognizer` (метка SVM, по умолчанию = uuid, не
отображаемое имя) ([A.5]). Значит, две персоны с одинаковым непустым
`nameInRecognizer` схлопнутся, а переименование безопасно. Для SYP: нужна ли
такая же двухфазная идентичность (человекочитаемое имя + технический ключ
модели), или достаточно одного идентификатора.

### Д-10. Плейсхолдер-типы персон

`UNDEFINDED` / `NONPERSON` / `EXTRAS` ([A.6], [C.6]) — не украшение:
`UNDEFINDED` = «распознано, не решено» (и именно они идут в следующий проход
распознавания), `NONPERSON` = фильтр мусора по `bbox aspect > 4`. Переносим ли
четыре типа или сокращаем до двух.
