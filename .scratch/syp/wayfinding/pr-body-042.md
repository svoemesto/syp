## Что сделано

Подсистема нотификаций SSE для админской части — по решению владельца
2026-10-03 «стиль нотификаций SSE как в Караоке» (ADR-0017). До этой порции SSE
в проекте не было нигде: ни сервера, ни клиента, ни зависимости.

| Пункт требования | Как сделано |
|---|---|
| 1. Образец Караоки: `SseEmitter`, вкладки, тип как имя события, heartbeat, клиентский таймаут выше серверного | Всё перенесено; см. ADR-0017 |
| 2. Идентификатор вкладки от клиента, значение из адреса недоверенное | Клиент генерирует и хранит в `sessionStorage`; сервер проверяет форму и подставляет свой идентификатор, если значение негодное |
| 3. Значение вкладки обязательно снимается после запроса | `TabIdContext` + фильтр, снятие в `finally`; проверяется тестом, в том числе на упавшем запросе |
| 4. Клиент — `event-source-polyfill` | Подключён в админской части; в публичной подписки нет (см. «Что осталось за рамками») |
| 5. Типы уведомлений свои, по домену | `jobProgress`, `jobState`, `queueState`, `checksumChanged`, `recipeReady`, `error`; караокинские имена запрещены тестом |
| 6. Отказ соединения не оставляет интерфейс мёртвым | До 5 попыток с растущей паузой, затем остановка **с текстом** и кнопкой «подключиться снова»; индикатор состояния, сводка очереди и ход задания в шапке всегда |
| 7. Проверки | `compileKotlin`, `ktlintCheck`, `bootJar`, `lint-docs`, `lint && build && format:check` в обоих фронтендах — зелёные; Docker не трогался |
| 8. Контракты и живая документация | `contracts/admin-api.md` § 11 (подписка, типы событий, инварианты тел, источники), ADR-0017, guideline `docs/guidelines/sse-notifications.md`, `job-queue.md`, per-feature документ, память проекта |

## Архитектура

- `JobQueueListener` в `syp-core`: очередь сообщает о каждой смене состояния и
  о движении прогресса. Слушатель висит **на очереди**, а не на воркере и не
  на контроллерах: очередь — единственное место, где меняется состояние
  задания, и повесь уведомление на воркера — отмена задания оператором
  останется незамеченной. Обратная связь запрещена: из обработчика нельзя
  изменить состояние задания в обход проверки переходов.
- `SseNotificationService`: реестр подключений по идентификатору вкладки,
  сердцебие комментарием раз в 15 секунд, снятие подписки при неудачной
  отправке. Канал отправки отделён от сервиса — проверка идёт на список
  отправленного, а не по сети.
- `deploy/nginx.conf`: отдельный `location = /api/subscribe` с выключенной
  буферизацией; `spring.mvc.async.request-timeout: -1`, иначе контейнер обрывал
  бы живую подписку на 30-й секунде.
