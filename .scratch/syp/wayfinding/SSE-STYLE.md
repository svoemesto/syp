# Нотификации SSE — стиль Караоки (решение владельца 2026-10-03)

«Стиль нотификаций SSE сделать как в Караоке.»

**У нас SSE нет вообще** — ни сервера, ни клиента, ни зависимости. Это новая
подсистема, а не правка стиля.

## Что сделано в Караоке (проверено, это моя выборка)

Бэкенд `/home/nsa/Karaoke/karaoke-app`:
- `services/SseNotificationService.kt` (250 строк) — `SseEmitter` на каждого
  подключённого; ключ подключения `(userId, browserTabId)`, то есть **вкладки
  различаются**;
- `TabIdContext` — `ThreadLocal` с идентификатором вкладки, ставится фильтром
  на входе запроса и **обязательно очищается в finally**, иначе значение
  «протечёт» в следующий несвязанный запрос;
- типы уведомлений — `model/SseNotificationType.kt`: `recordChange`,
  `recordAdd`, `recordDelete`, `processWorkerState`, `processCountWaiting`,
  `cacheQueueSize`, `message`, `error`, `dummy`, `log` и другие. **Имя типа
  едет в SSE как имя события**, а не как поле в общем потоке;
- heartbeat раз в 15 секунд.

Фронтенд `/home/nsa/Karaoke/webvue3`:
- `EventSourcePolyfill` из пакета `event-source-polyfill`, не нативный
  `EventSource`;
- подключение: `/api/subscribe?tabId=<идентификатор вкладки>`;
- `heartbeatTimeout: 30000` — **больше серверного heartbeat (15 с) и меньше
  дефолта полифилла**, и это подписано в коде;
- слушатели навешиваются по именам: `msgServer.addEventListener('user', …)`,
  то есть обработчик на тип, а не один на всё.

## Требования к порции

1. Реализовать по этому образцу, а не по-своему: сервер на `SseEmitter`,
   различение вкладок, тип уведомления как имя события, heartbeat и клиентский
   таймаут выше серверного.
2. Идентификатор вкладки клиент генерирует сам и передаёт в адресе. Значение
   из пути/адреса **нельзя принимать как доверенное**: оно приходит от клиента.
3. `TabIdContext`-подобное значение **обязательно очищается** после запроса.
4. Клиент — `event-source-polyfill`, оба фронтенда, где это нужно.
5. Типы уведомлений SYP — свои, по домену: ход задания и состояние очереди,
   изменение суммы, готовность сценария, ошибка. Не тащить караокинские имена
   (`recordChange`, `cacheQueueSize`) — они про чужой домен.
6. Отказ соединения не должен оставлять интерфейс мёртвым: переподключение с
   понятным состоянием, а не бесконечный молчаливый retry.
7. Проверка: `npm run lint && npm run build && npm run format:check` в обоих
   фронтендах, компиляция и ktlint бэкенда, `lint-docs.py`. Docker не трогать.
8. Обновить контракты и живу��ую документацию: новый эндпоинт подписки и типы
   событий должны быть описаны в `contracts/admin-api.md`.
