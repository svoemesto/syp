# SYP Constitution

Этот документ определяет непреложные принципы проекта SYP (Show Your Picture),
его стек, ограничения и порядок внесения изменений. При расхождении с
`AGENTS.md` приоритет у настоящей Конституции; `AGENTS.md` уточняет её, но не
отменяет.

## Core Principles

> **Формат**: каждый Principle — название, короткое утверждение, ссылка на
> детали. Детали реализации живут в `docs/`, ADR и per-feature документах.
> Основание правил — проект `Karaoke` (constitution v2.4.0), перенесено при
> bootstrap 2026-10-01.

### I. Язык общения — только русский (NON-NEGOTIABLE)

**Rule**: Всё общение с владельцем — на русском. Документация, комментарии в
коде, коммиты, ADR — на русском. Ответ на иностранном без запроса владельца —
нарушение.

**Детали**: `AGENTS.md` § Tier-0.

### II. Knowledge-first pre-flight (NON-NEGOTIABLE)

**Rule**: Перед любой фичей, спекой или правкой — сначала живые документы
проекта, потом код. Порядок: карта документов → поиск по ним (не менее трёх
попыток с разными ключами) → домен и его компоненты → все ADR → и только
потом код.

**Источник знаний о старом проекте**: `/home/nsa/ivfx4/legacy-analysis/` —
читать можно, **код оттуда не переносится**. Находка, влияющая на модель,
проходит через обсуждение с владельцем и ложится в ADR.

**Failure**: если релевантных документов не нашлось — спека обязана явно
записать «Searched: … → no relevant docs», а не молчать.

**Детали**: `AGENTS.md` § Tier-1 MUST #0; секция «Knowledge References» в
каждой `spec.md` — обязательна.

### III. Сырой JDBC, JPA запрещена (NON-NEGOTIABLE)

**Rule**: Персистентность — прямой доступ к базе по образцу `KaraokeDbTable`
(reflection + diff-based save, `recordhash`). Запрещены `spring-boot-starter-data-jpa`,
`jakarta.persistence`, `javax.persistence`, автогенерация схемы. Миграции БД —
нумерованные, **append-only**, Postgres 16.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Стек и запреты»; ADR-0001 проекта
Karaoke как образец.

### IV. Долгие операции — только через очередь (NON-NEGOTIABLE)

**Rule**: Всё, что дольше нескольких секунд, выполняется заданием в очереди с
наблюдаемым состоянием. Код возврата внешней программы **обязан проверяться**;
ошибка не может выглядеть как успех. Запись артефакта атомарна: незавершённый
файл не считается готовым.

**Детали**: `AGENTS.md` § Tier-1 (образец «Очередь перед перезапуском»);
ADR-0006 Karaoke — `redirectErrorStream`.

### V. Секреты — только через окружение (NON-NEGOTIABLE)

**Rule**: Ни один секрет не попадает в код и не коммитится. Передача — через
переменные окружения. `.gitignore` недостаточен для уже отслеживаемых файлов —
нужен `git rm --cached`. Обнаруженный утёкший секрет меняется **до** удаления
из истории. Секреты не печатаются в вывод и логи.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Secrets & git hygiene».

### VI. Спецификация — контракт (NON-NEGOTIABLE)

**Rule**: `spec.md` после утверждения владельцем не переписывается агентом.
Изменение функциональных требований или критериев успеха — только по слову
владельца. Агенту запрещено «дорабатывать» спеку молча, даже если правка
выглядит очевидной.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Процесс: wayfinder → исполнение».

### VII. Git: master закрыт (NON-NEGOTIABLE)

**Rule**: Прямые коммиты и push в `master` запрещены. Только feature-ветка →
запрос на слияние → проверки → слияние. Ветка `master` защищена: принудительный
push и удаление запрещены, требуется одобрение.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Git — CI-gate для master».

### VIII. Living docs — единственный источник (NON-NEGOTIABLE)

**Rule**: Изменение в коде требует синхронного изменения документации. У каждой
фичи есть документ с описанием; он обновляется в том же изменении, что и код.
Решения фиксируются в ADR, которые только дополняются, а не переписываются.
Каждое правило живёт в одном файле — дублей быть не должно.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Living docs SSoT»;
`docs/features/<slug>.md`, `docs/adr/`.

### IX. Процесс: карта решений → исполнение (NON-NEGOTIABLE)

**Rule**: Большая неясная задача начинается с карты решений: назначение,
известное, неизвестное, вне области. Задачи и решения живут в трекере проекта,
не в локальных файлах. Одна сессия закрывает не более одного тикета-решения
(исследовательские — можно параллельно). Классификацию остатка выбирает
владелец: «большая» идёт по спеке цепочкой, «маленькая» — напрямую.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Процесс: wayfinder → исполнение»;
`~/.dsh/romario-team/wayfinding-operations.md`, `subagents.md`.

## Технологический стек

**Rule**: Стек SYP — как в Karaoke: контейнеры, Kotlin/Spring Boot, Vue 3,
Postgres 16, объектное хранилище, очередь заданий. Шесть контейнеров: база,
хранилище, админка (бэкенд и фронтенд), публичная часть (бэкенд и фронтенд).
Подготовка и настройка — только в админке; публичная часть только показывает
результат. Смешивать ответственность двух фронтендов запрещено.

**Видео**: обработка через ffmpeg; домен оперирует сценами, а не файлами
`.mp4`. Перекодирование в первом срезе не применяется — склейка выборки идёт
без перекодирования, округление по границам ключевых кадров на стыках
допускается как осознанное решение владельца.

**Детали**: `AGENTS.md` § Tier-1 Hard Gates «Контейнеры», «Build / Deploy /
Containers», «Трекер».

## Процесс разработки

**Rule**: Любое изменение проходит путь: решение зафиксировано → спека →
план → задачи → реализация → проверка → merge → отчёт в трекере → ревью →
закрытие. Отчёт обязателен и публикуется **до** перевода задачи на ревью.

**Субагенты**: работа параллельных задач ведётся в отдельных рабочих копиях
репозитория, а не в одной. Проверка чужой работы назначается владельцем
явно; агент по умолчанию проверяет сам себя по фактам на диске.

**Детали**: `AGENTS.md` § Tier-1 (Hard Gate «Subagent workspace isolation»,
«Трекер: OpenProject»).

## Governance

Конституция выше любой практики. Правки:

- требуют явного изменения версии (semver) и описания последствий;
- проходят через отдельное изменение (governance-PR), а не по ходу фичи;
- согласуются владельцем: защита `master` требует его одобрения.

Новый принцип сначала проверяется на «не противоречит ли он уже принятым
решениям», затем ложится в этот документ с указанием основания.
Все проверки соответствия обязаны ссылаться на этот документ.
