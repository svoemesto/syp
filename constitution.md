# SYP Constitution

Этот документ определяет непреложные принципы, технологический стек,
ограничения доступа и процедуру внесения изменений для проекта `SYP`
(Show Your Picture, svoemesto). При расхождении с `AGENTS.md` приоритет —
у Конституции; вторичные правила уточняют её, но не отменяют.

## Core Principles

> **Формат**: каждый Principle содержит **название**, **1-2 строки
> утверждения**, **enforcement** и **cross-reference** на детали. Это
> **нормативная база** — детали реализации живут в `docs/`, ADR и
> per-feature документах.

### I. Язык общения — только русский (NON-NEGOTIABLE)

**Rule**: Всё общение с владельцем, вся документация, комментарии в коде,
сообщения коммитов и ADR — **на русском**. Ответ на иностранном без запроса
владельца — нарушение.

**Детали**: `AGENTS.md` § Tier-0.

### II. Knowledge-first pre-flight (NON-NEGOTIABLE)

**Прецедент (Karaoke)**: spec #339 — агент изобрёл форму кеша вместо
паттерна из `knowledge/domains/caching/components/`. В SYP риск тот же и выше:
в проекте нет ни `docs/domains/`, ни `docs/adr/` — их создание отложено на
bootstrap, и агент обязан компенсировать это чтением отчётов по старому
проекту.

**Rule (II.1)**: Перед ЛЮБОЙ фичей, спекой или правкой — 5 шагов: карта
документов → не менее трёх поисков с разными ключами → домен и его
компоненты → все ADR → и только потом код.

**Rule (II.2)**: Источник знаний о старом проекте —
`/home/nsa/ivfx4/legacy-analysis/` — читать можно, **код оттуда не
переносится**. Находка, влияющая на модель, проходит через обсуждение с
владельцем и ложится в ADR.

**Failure-stop**: `codegraph_explore` / `grep` по коду ДО Knowledge-first =
нарушение Конституции. Поиск без результатов — зафиксировать в `spec.md`
явно («Searched: … → no relevant docs»), а не молчать.

**Enforcement**: `tools/spec-knowledge-preflight.sh` `[bootstrap]` +
обязательная секция «Knowledge References» в каждой `spec.md`.

**Single source of truth**: `AGENTS.md` § MUST #0 + этот документ § II.

### III. Сырой JDBC + дифф по хэшам (NON-NEGOTIABLE)

**Rule**: База — только через сырой JDBC (по образцу `KaraokeDbTable`).
Никаких JPA / Hibernate / Exposed. Автогенерация схемы запрещена. Миграции —
нумерованные, **append-only**, Postgres 16.

**Enforcement**: `tools/check-no-jpa-imports.sh` `[bootstrap]`.

**Детали**: образец — `AGENTS.md` § Tier-1 Hard Gate «Стек и запреты»;
ADR-0001 Karaoke.

### IV. Очередь заданий с обязательной проверкой кода возврата (NON-NEGOTIABLE)

**Прецедент (старый проект `ivfx4`)**: **ни один из 12 вызовов ffmpeg не
проверял код возврата** — упавший процесс помечался как «сделано», а
идемпотентность держалась только на флагах в базе. Это причина повреждённых
артефактов, а не гипотеза.

**Rule (IV.1)**: Длительные операции — только через очередь заданий с
наблюдаемым состоянием (работает / ждёт / ошибка / завершено). Кнопка,
блокирующая интерфейс на десятки секунд, — нарушение.

**Rule (IV.2)**: Код возврата внешней программы проверяется **всегда**.
Ошибка обязана выглядеть как ошибка.

**Rule (IV.3)**: Запись артефакта атомарна: незавершённый файл не считается
готовым. Результат задания зависит от версии алгоритма и параметров;
смена версии помечает старые результаты устаревшими.

**Rule (IV.4)**: «Сырой» результат автоматики хранится отдельно от ручных
правок оператора; повторный анализ не затирает то, что сделал человек.

**Enforcement**: `tools/check-ffmpeg-returncode.sh` `[bootstrap]`;
`redirectErrorStream(true)` обязательно (ADR-0006 Karaoke).

### V. Двух-фронтенд: админка и публичная часть — разные приложения (NON-NEGOTIABLE)

**Rule**: `syp-admin-web` и `syp-public-web` — **разные приложения**.
Подготовка, разметка, обучение моделей — только в админке. Публичная часть
**только показывает результат**. Смешивание ответственности ЗАПРЕЩЕНО.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Контейнеры».

### VI. Code Standards (NON-NEGOTIABLE)

**Rule (VI.1, FR-006)**: публичные API MUST иметь KDoc/JSDoc со ссылкой на
per-feature документ.

**Rule (VI.2, FR-007)**: линтеры — в pre-commit и CI. Baseline допускается,
но CI падает на **новые** нарушения.

**Rule (VI.3, FR-009)**: при правке кода MUST обновить per-feature документ
в том же изменении.

**Enforcement**: ktlint / ESLint в CI `[bootstrap]`;
`tools/check-feature-doc.sh` `[bootstrap]`.

### VII. Git: `master` закрыт (NON-NEGOTIABLE)

**Rule (VII.1)**: Прямые `git commit` / `git push` в `master` запрещены.
Только feature-ветка → запрос на слияние → проверки → слияние.

**Rule (VII.2)**: ветка `master` защищена: принудительный push и удаление
запрещены, требуется одно одобрение. Создано 2026-10-02 при bootstrap
репозитория.

**Rule (VII.3)**: параллельные задачи ведутся в отдельных рабочих копиях
(`git worktree`), а не в одной: два субагента в одном рабочем каталоге
кончаются часами на переносе чужих изменений.

**Rule (VII.4)**: сообщения коммитов — на русском, коротко и по существу.

**Rule (VII.5)**: имя feature-ветки — **`NNN-<slug>`**, где `NNN`
резервируется скриптом `tools/reserve-branch-number.sh`, а не придумывается.
Номер выбирается как следующий свободный по трём источникам: ветки на
`origin`, теги-резервации `seq/NNN`, каталоги `specs/`. Резервация атомарна:
она делается push уникального lightweight-тега `refs/tags/seq/NNN` в
`origin` — git отклоняет push, если тег с таким именем уже есть, что даёт
сравнение-и-обмен без отдельного сервера. Теги живут дольше веток, поэтому
история нумерации не теряется после удаления смерженной ветки.

**Enforcement**: branch protection на GitHub; резервная нумерация —
`tools/reserve-branch-number.sh` (перенесён из Karaoke 2026-10-02);
`tools/check-subagent-isolation.sh` `[bootstrap]`.

### VIII. Секреты и git-гигиена (NON-NEGOTIABLE)

**Прецедент (Karaoke, 2026-08-03)**: `deploy/.env` с паролями Postgres, MinIO
и Docker Hub протёк в публичный репозиторий и оставался там 3 года.

**Rule (VIII.1)**: секрет-файлы MUST быть в `.gitignore` **и** не отслеживаться
git. `.gitignore` НЕ достаточно — для уже отслеживаемых файлов обязателен
`git rm --cached`.

**Rule (VIII.2)**: никогда не коммитить: `.env`, `.env.local-tracker`,
`deploy/.env`, `deploy/do.env`, `*.key`, `*.pem`, `*.p12`, `*.pfx`, `logs/`,
`node_modules/`, `dist/`.

**Rule (VIII.3)**: проверка перед коммитом обязательна:
`git ls-files | grep -iE '\.env$|\.key$|\.pem$|\.p12$|\.pfx$'` MUST быть пусто.

**Rule (VIII.4)**: при обнаружении утёкшего секрета — **сначала** сменить
секрет, **потом** `git rm --cached`, **потом** опционально переписать историю.

**Rule (VIII.5)**: секреты в коде запрещены — только через переменные
окружения. Дефолт допустим, только если он невалидный или публичный.

**Rule (VIII.6)**: секреты не печатаются в вывод и логи.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Secrets & git hygiene».

### IX. Процесс: карта решений → спецификация → исполнение (NON-NEGOTIABLE)

**Rule (IX.1)**: большая неясная задача начинается с карты решений в трекере
(назначение / известное / неизвестное / вне области). Задачи и решения живут
в трекере проекта (`syp`, id 4), а не в локальных файлах.

**Rule (IX.2)**: одна сессия закрывает **не более одного** тикета-решения;
исследовательские тикеты можно вести параллельно. Claim — до первой строки
работы.

**Rule (IX.3)**: классификацию остатка выбирает владелец: «большая» идёт по
спеке цепочкой (`specify` → план → задачи → анализ → реализация), «маленькая»
— напрямую.

**Rule (IX.4)**: **спецификация — контракт.** После утверждения владельцем FR и
SC не переписываются агентом. Изменение — только по слову владельца.

**Rule (IX.5)**: спека уходит владельцу и **ждёт**. Без его слова цепочка не
идёт дальше.

**Детали**: `AGENTS.md` § Tier-1 Hard Gate «Процесс: wayfinder → исполнение»;
`~/.dsh/romario-team/wayfinding-operations.md`, `subagents.md`.

## Технологический стек

- **Контейнеры**: ровно шесть. `syp-db` (Postgres 16), `syp-storage` (MinIO),
  `syp-admin-app` + `syp-admin-web` (админка: разметка, анализ, очередь),
  `syp-public-app` + `syp-public-web` (публичная часть: только результат).
- **Backend**: Kotlin + Spring Boot, Gradle multi-module. Персистентность —
  сырой JDBC.
- **Frontend**: Vue 3 + Vite. Каталог фронтенда = имя контейнера; в корне
  проекта `package.json` нет, `npm run` из корня не работает.
- **Хранилище**: Postgres 16 (сырой JDBC), MinIO (превью кадров и
  промежуточные файлы), готовые видеофайлы — на HDD.
- **Видео**: ffmpeg. Домен оперирует **сценами и планами**, а не файлами
  `.mp4`. Детектор границ сцен — встроенный фильтр ffmpeg; перенос
  GUI-автоматизации из старого проекта запрещён.
- **Перекодирование**: в первом вертикальном срезе **не применяется**.
  Склейка выборки идёт без перекодирования; округление границ до ключевых
  кадров на стыках — осознанное решение владельца, а не дефект.
- **GPU**: основной режим вычислений — GPU. На машине разработки 16 ГБ VRAM;
  в среде, где работает агент, видеокарты **нет** — замеры и проверки идут
  через контейнер.
- **Диски**: исходные видео — только для чтения. Превью и промежуточные
  файлы — SSD, готовые видеофайлы — HDD. Решение владельца от 2026-10-02.
- **Порты**: веб — диапазон 7910–7999, хранилище — 9020–9099; фиксируются при
  bootstrap развёртывания.
- **Деплой-окружения**: одно — локальная машина. Публикация в интернет не
  планируется.

## Ограничения и доступы агента

Эти правила имеют приоритет над `AGENTS.md` в случае конфликта.

**Категорически запрещено агенту:**

1. Перезапускать контейнер SYP с активными заданиями. Разрешение владельца на
   перезапуск означает согласие на перезапуск **после остановки очереди**:
   сначала убедиться, что заданий в работе нет, остановить очередь, дождаться
   фактической остановки, и только затем перезапускать. Разрешение на
   конкретный перезапуск **не продлевается** на следующие в той же сессии.
2. Перезапускать контейнер мимо `deploy/do.sh`. `docker restart` запрещён.
3. Публиковать что-либо в интернет — весь стек локальный.
4. Коммитить секрет-файлы (полный список — Principle VIII.2).
5. Печатать секреты в вывод и логи.
6. Править спецификацию (`spec.md`) после её утверждения владельцем — только
   по слову владельца.
7. Идти в код раньше Knowledge-first pre-flight (Principle II).
8. Тащить **код** из `/home/nsa/ivfx4` — читать можно, код не переносится.
9. Делать выводы о правах доступа к дискам по данным песочницы агента:
   в ней всё смонтировано только для чтения, включая корень, в который при
   этом писать можно. Проверять контейнером на хосте.
10. Объявлять результат замера, проведённого в песочнице агента, надёжным:
    `ffmpeg` там обрывается `signal 9` на длинных операциях.

**Разрешено агенту:**

1. Редактировать любой код проекта, создавать миграции (append-only),
   писать тесты и документацию.
2. Собирать backend через `./gradlew` с
   `GRADLE_USER_HOME=/home/nsa/syp/.gradle`; docker — с
   `DOCKER_CONFIG=/home/nsa/syp/.docker`.
3. Собирать фронтенды только из их каталогов:
   `cd syp-admin-web && npm run build`.
4. Запускать одноразовые контейнеры для проверки фактов о среде (например,
   смонтировать диск и проверить запись) — без пересборки и перезапуска
   контейнеров SYP.
5. Замерять видео-часть пайплайна (декодирование, детекция границ, нарезка,
   склейка) — с оговоркой пункта 10 выше.
6. Работать с трекером проекта `syp` только через `tools/tracker.sh`; прямой
   доступ к API OpenProject запрещён.

## Рабочий процесс

- **Backend-сборка**:
  `GRADLE_USER_HOME=/home/nsa/syp/.gradle ./gradlew compileKotlin --parallel`.
  Параллельные сборки над одним рабочим каталогом запрещены.
- **Линтеры**: `GRADLE_USER_HOME=/home/nsa/syp/.gradle ./gradlew ktlintCheck`;
  в каждом каталоге фронтенда — `npm run lint`.
- **Docker**: сборка образов только через `deploy/do.sh` с
  `DOCKER_CONFIG=/home/nsa/syp/.docker`; управление контейнерами — только
  `start_*` / `restart_*` из этого же скрипта.
- **Диагностика**: при разборе сбоя сначала `docker logs <контейнер>`, потом
  гипотезы.
- **Git**: не коммитить без явного запроса владельца. Перед `git add` —
  `git status` + `git diff --stat`. Перед коммитом — проверка секретов
  (Principle VIII.3).
- **Память проекта**: `docs/STATE-OF-PLAY.md` — первое, что читает новая
  сессия; ответ «Продолжай» без его чтения — потеря контекста.
- **Тесты**: CI пока нет; проверка после изменения обязательна вручную по
  списку в `AGENTS.md` § Tier-2.

## Governance

1. **Приоритет**: Конституция > `AGENTS.md` > остальные документы.
   Конституция фиксирует непреложные принципы; `AGENTS.md` — рабочие
   инструкции; `docs/` — детали и проектная память.
2. **Внесение изменений**: каждое изменение Конституции оформляется отдельным
   запросом на слияние с сообщением
   `docs: amend constitution to vX.Y.Z (краткое описание)`. В теле изменения
   указывается Sync Impact Report (какие принципы добавлены, изменены, удалены;
   какие артефакты требуют синхронизации; что осталось нерешённым).
3. **Версионирование (semver)**:
   - **MAJOR** (X.0.0) — обратно несовместимое изменение governance:
     удаление принципа, переопределение его смысла, изменение ограничений
     доступа агента.
   - **MINOR** (x.Y.0) — добавление принципа, секции, существенное расширение
     существующего принципа.
   - **PATCH** (x.y.Z) — уточнения формулировок, опечатки, несемантические
     правки, обновление ссылок.
4. **Compliance review**: каждое изменение, проходящее через план или ревью
   кода, обязано проверить соответствие всем Core Principles. Нарушение
   обосновывается явно в плане, а не замалчивается.
5. **Sync-обязательства**: при изменении принципа обновить все зависящие
   артефакты (шаблоны плана, спецификации, задач; `AGENTS.md`; per-feature
   документы). Sync Impact Report пишется комментарием в начале файла.
6. **Ратификация**: документ вступает в силу с момента слияния запроса на
   слияние владельцем; до этого статус — `pending`.
