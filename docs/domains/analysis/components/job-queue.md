# Спецификация компонента: Очередь заданий

Домен: [Analysis](../domain.md) — очередь обслуживает все домены, но именно
анализ и лица её нагружают. Спецификация: `specs/001-first-vertical-slice/`,
контракт `contracts/job-queue.md`.

## Ответственность | Responsibility

Компонент даёт наблюдаемое состояние работы и различает «не выполнено»,
«выполнено» и «не удалось». Без него ни одна длинная операция не может быть
ни запущена, ни отменена, ни проверена (constitution IV).

## Интерфейсы и Контракты | Interfaces and Contracts

- **Постановка в очередь**: вид задания, предмет работы, параметры, хеш
  параметров → идентификатор задания.
- **Захват**: список допустимых видов → взятое задание или «очередь пуста».
  Захват атомарен: два воркера не получат одно задание.
- **Переход состояния**: `WAITING → CREATING → WORKING → DONE`, плюс переход в
  `ERROR` из любого состояния. Недопустимый переход отклоняется **до** записи.
- **Прогресс**: сделано, всего, пояснение. Прогресс монотонен и хранится в
  базе, а не в памяти воркера, — поэтому переживает перезапуск.
- **Отмена оператором**: задание возвращается в очередь **с сохранённым
  прогрессом**, работа не начинается заново молча.
- **Пропуск выполненной работы**: вид задания и хеш параметров → признак
  «результат зарегистрирован как `READY`».

## Логика и Алгоритмы | Logic and Algorithms

1. **Состояний ровно пять.** `WAITING`, `CREATING`, `WORKING`, `DONE`,
   `ERROR`. Меньше нельзя — оператор не отличит «взято» от «идёт»; больше
   нельзя — лишнее состояние всегда означает нерешённый вопрос «что с ним
   делать».
2. **Таблица разрешённых переходов объявлена явно.** Проверка идёт до записи,
   поэтому неверный переход даёт отказ с внятным текстом, а не тихую порчу
   состояния.
3. **Прогресс монотонен.** Уменьшение прогресса считается ошибкой вызывающего
   кода. Общий объём работы показывается интерфейсом, когда он известен; до
   того доля выполнения не выдумывается.
4. **Выход из `ERROR` — только явной повторной постановкой.** Молчаливый
   автоматический повтор скрывает неисправность, а SC-005 требует, чтобы
   ошибка была видна.
5. **Пропуск задания разрешён только при зарегистрированном результате.** «Файл
   есть» не означает «работа выполнена»: проверяется регистрация артефакта в
   состоянии `READY` для того же хеша параметров (Р-10).
6. **Смена параметров помечает старые результаты устаревшими, но не удаляет их
   и не запускает пересчёт.** Автоматический пересчёт уничтожил бы ручные
   правки оператора (SC-006).
7. **Исполнитель есть только у админского бэкенда.** Он берёт `ANALYZE`,
   `FACES`, `TRAIN`, `HASH`. Вида `ASSEMBLE` не существует: сборка подборки
   выполняется на машине пользователя (ADR-0009, research.md Т-20).

## Зависимости | Dependencies

- → `Catalog` (параметры эпизода, ради которых ставятся задания).
- → [artifact-registry](artifact-registry.md) (регистрация результата, по
  которой принимается решение о пропуске).
- → внешние программы: запуск только через единый исполнитель, с проверкой
  кода возврата.
- → нотификации интерфейса (один поток SSE): очередь сообщает о каждой смене
  состояния и о движении прогресса, иначе единственный способ узнать о
  завершении работы — повторно спросить сервер. Наблюдатель висит **на
  очереди**, а не на воркере и не на контроллерах: повесь уведомление на
  воркера, и отмена задания оператором останется незамеченной. Образец —
  [guideline по нотификациям](../../../guidelines/sse-notifications.md).
