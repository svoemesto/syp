# Спецификация компонента: Воркер на машине пользователя

Домен: [Showcase](../domain.md). Спецификация: `specs/001-first-vertical-slice/`.

## Ответственность | Responsibility

Воркер — программа, которая живёт **на машине пользователя**, а не в стеке
сервера. Он наблюдает каталог сценариев, выполняет появившийся сценарий и
фиксирует результат выполнения. Готовый файл остаётся у пользователя.

Воркер отвечает за три вещи, каждая из которых легко потерять:

1. **не выполнить подделку** — сценарий пришёл из интернета и прошёл через
   браузер, доверять ему нельзя;
2. **не тратить впустую время пользователя** — все проверки до начала работы,
   а не по ходу;
3. **не объявить успехом ошибку** — код возврата каждой внешней программы
   проверяется всегда, как и на сервере (constitution IV.2).

## Интерфейсы и Контракты | Interfaces and Contracts

- **Наблюдение за каталогом**: появление файла сценария → обработка по одному
  файлу за проход, с записью каждого действия в журнал.
- **Проверка среды**: → перечень того, чего не хватает, с указанием, что
  установить.
- **Проверка подписи**: файл сценария, доверенный открытый ключ → признак
  «подлинно» либо отказ с названием файла.
- **Сверка целостности**: список фрагментов, корни каталогов → признак «можно
  резать» либо отказ с названием несовпавшего файла.
- **Сборка**: проверенный сценарий → готовый файл и отчёт о выполнении.
- **Каталог обработанных**: результат обработки файла сценария.

## Логика и Алгоритмы

1. **Сценарий — данные, а не программа.** Воркер **не выполняет** файл: он
   разбирает его как структурированные данные и выполняет собственную логику.
   Образец воркера Karaoke выполняет найденный `.sh` напрямую; здесь источник
   недоверенный, и выполнение файла означало бы запуск чужого кода на машине
   пользователя. Проверка подписи уменьшает риск, но не отменяет принципа.
2. **Порядок проверок не переставляется.** Среда, подпись, версия формата,
   структура каталогов, фильм, суммы — и только потом нарезка. Каждая
   проверка дешевле следующего шага, а отказ после начала работы стоит
   пользователю часа ожидания впустую.
3. **Сверяются все файлы до первой нарезки.** Не «по мере нарезки»: подмена
   обнаруживается за секунды, а не через час.
4. **Суммы кэшируются по паре «размер + время изменения».** Повторный запуск
   того же сценария не читает диск заново; изменённый файл обнаруживается
   снова.
5. **Нарезка от ближайшего ключевого кадра, склейка потоковым копированием.**
   Перекодирования нет (ADR-0006). Начало фрагмента — фактическая граница из
   сценария, а не расчётная.
6. **Код возврата каждой внешней программы проверяется.** Упавший `ffmpeg`
   даёт ошибку в журнале и ненулевой код возврата воркера, а не «готово». В
   старом проекте не проверял код возврата ни один вызов ffmpeg; на машине
   пользоваента это означало бы, что битый файл выдаётся за подборку.
7. **Результат пишется атомарно.** Файл появляется под окончательным именем
   только целиком; прерванный файл не остаётся «полуготовым» (FR-091).
8. **Фактические величины измеряются заново** и кладутся в отчёт рядом с
   расчётными из сценария, с указанием причины расхождения (FR-083).
9. **Обработанный сценарий переносится, а не удаляется.** После сбоя
   пользователь должен иметь возможность разобраться.
10. **На сервер воркер не обращается** ни во время работы, ни после неё, и
    ничего на сервер не отправляет (FR-089e).

## Зависимости | Dependencies

- → сценарий сборки: источник фрагментов, границ, сумм и данных для показа.
- → доверенный открытый ключ: чем проверяется подпись.
- → `ffmpeg`, `ffprobe`, `openssl`: внешние программы; наличие проверяется до
  работы.
- → копия дерева фильма у пользователя: источник нарезки (FR-089a).
- → `local-player`: запуск показа по итогам сборки.
