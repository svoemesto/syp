# ADR-0009: Сервер отдаёт рецепт сборки, а не видеофайл

## Context & Problem | Контекст и проблема

Исходный архив сериала — 73 файла, 360 ГБ, 69,1 часа видео. По исходной схеме
сервер держит их постоянно, анализирует и **собирает подборку сам**, а
публичная часть отдаёт пользователю готовый видеофайл.

Эта схема плохо масштабируется в двух направлениях:

1. **Хранение.** Размещение 360 ГБ в интернете стоит денег, а архив растёт с
   каждым новым сериалом.
2. **Передача.** Каждый показ — это передача видео зрителю: трафик, ожидание,
   хранение результатов на сервере.

При этом исходники у пользователя **уже есть**: он работает со своим сериалом
и держит свою копию.

Прецедент в проекте Karaoke: там часть работы уже уходит на машину
пользователя — воркер `karaoke_watcher.sh` наблюдает каталог, выполняет
появившиеся сценарии и запускает плеер.

## Decision | Решение

**Сервер не хранит и не передаёт видеофайлы подборок. Он формирует рецепт.**

1. Анализ остаётся на сервере и остаётся задачей администратора: сервер держит
   исходники, прогоняет детект сцен и лиц, обучает модели, хранит метаданные.
2. Публичная часть по запросу пользователя формирует **сценарий сборки** —
   исполняемый рецепт со списком фрагментов: относительные пути и границы по
   номерам кадров.
3. Доставка сценария — **ручная**: пользователь скачивает файл через браузер и
   сам помещает его в каталог. Автоматическая доставка (ссылка с подпиской,
   обновление, докачивание) сознательно **не проектируется**: в первом срезе
   объём ограничен, а образца работающей доставки нет и в Karaoke — папка
   воркера там пуста и не смонтирована ни в одном compose-файле.
4. На машине пользователя работает **воркер**: наблюдает каталог сценариев,
   проверяет подпись сценария и суммы файлов, режет фрагменты, склеивает их в
   один файл **без перекодирования** (ADR-0006) и запускает локальный показ со
   списком сцен.
5. Готовый файл остаётся на машине пользователя; загрузки на сайт не
   происходит.

Это возможно именно потому, что ADR-0006 запрещает перекодирование: рецепт
работает без качественных потерь, а значит, видео не нужно гонять по сети.

## Rationale | Обоснование

- **Альтернатива: сервер собирает и отдаёт файл.** Требует хранения архива и
  передачи видео каждому зрителю. Дорого по трафику и диску, растёт линейно с
  числом пользователей.
- **Альтернатива: отдавать готовый файл только по запросу, без хранения.**
  Передача остаётся, хранение снимается, но пользователь всё равно ждёт выгрузки
  и тратит трафик.
- **Альтернатива: отдавать пользователю метаданные и требовать собирать
  самостоятельно.** Отвергнуто: сборка требует понимания форматов, таймкодов и
  кодеков. Рецепт делает работу за пользователя.

## Consequences | Последствия

1. **Запрет**: не добавлять в публичную часть хранение, приём или передачу
   видеофайлов.
2. **Инвариант**: по сети передаётся только текст сценария; исходное видео не
   покидает машину администратора.
3. **Инвариант**: сценарий непригоден без исходников — пользователь обязан
   иметь копию сериала с той же структурой каталогов.
4. **Инвариант**: воркер проверяет подпись сценария **до** выполнения и суммы
   файлов **до** нарезки, иначе подмена файла обнаружится через час работы.
5. **Требуется**: образец для воркера — `karaoke_watcher.sh` проекта Karaoke.
   Его подход (наблюдение за каталогом, выполнение, проверка кода возврата,
   удаление выполненного) переносится, но **дополняется проверкой подписи**:
   в Karaoke источник доверенный, здесь сценарий приходит из интернета.
6. **Требуется**: справочник сумм `sha256` исходников на сервере — эталон
   проверки. Считается один раз, хранится рядом с метаданными сериала.
7. **Требуется**: ошибки пользовательской среды (нет `ffmpeg`, нет файлов,
   нет прав) диагностируются **до** начала работы, а не в середине.
8. **Инвариант**: ручное действие пользователя не отменяет проверку. Файл
   прошёл через браузер и диск пользователя — подпись и `sha256` проверяются
   **до** выполнения и **до** нарезки соответственно. Без этого подмена
   обнаружится через час работы, а не на первой секунде.

## Что осталось неизменным

- Анализ на сервере, задача администратора.
- Точность границ до номера кадра в данных (ADR-0001).
- Сборка без перекодирования, округление до ключевого кадра на стыках
  допускается как осознанное решение (ADR-0006).
- Универсальный исполнитель фильтров (ADR-0008).

## Примечание об исправлении факта (2026-10-02)

«69,1 часа видео» в тексте выше **неверно**: замер `ffprobe` по всем 73 файлам
даёт **70,00 ч** и 6 042 173 кадра. Текст решения не правится — ADR
неизменяем; исправленный факт фиксируется здесь.

## Уточнение решения владельца (2026-10-02): сверка сумм с кэшем

Полная сверка `sha256` всех нужных исходников до начала работы потребовала бы
чтения десятков гигабайт (подборка из десяти серий — 56 ГБ), что конфликтует с
критерием SC-004. Владелец выбрал: **полная сверка при первом запуске**, при
повторных — сверка по признакам «размер + время изменения» с кэшем.

**Что это не ловит:** подмена файла с сохранением размера и времени изменения
останется незамеченной. Это осознанный размен: быстрота повторных запусков в
обмен на узкий класс подмены, вероятный только при намеренной подмене с
сохранением метаданных. Воркер обязан показывать пользователю, по какому
признаку файл признан совпадающим (FR-089g).
