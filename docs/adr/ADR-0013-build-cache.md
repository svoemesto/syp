# ADR-0013: Кеш колёс при сборке образов

**Статус**: принято
**Дата**: 2026-10-03

## Context & Problem | Контекст и проблема

Образ бэкенда ставит `onnxruntime-gpu` и девять колёс NVIDIA CUDA 12. Вместе это
около двух гигабайт, и каждый образ тянет их из сети сам. При этом шаг установки
был написан как `pip install --no-cache-dir` с последующим `rm -rf
/root/.cache` — кеш выключался дважды, явно и по замыслу.

Следствие: пересборка образа после правки кода, не относящейся к нейросетям,
стоила полной перекачки двух гигабайт. Сборка админки и публичного образа идут
дольше таймаута инструментов, и одна из них была убита именно этим.

## Decision | Решение

Шаг установки выполняется с кешем pip в слое BuildKit:

```
RUN --mount=type=cache,target=/root/.cache/pip,sharing=locked \
    pip install --break-system-packages ...
```

Директива `# syntax=docker/dockerfile:1.7` объявлена в начале файла — без неё
cache mount не собирается.

## Rationale | Обоснование

Cache mount не является слоем образа: кеш живёт отдельно и переживает
пересборки, а в образ не попадает. Флаги, которые выключали кеш, удалены
навсегда: `--no-cache-dir` запрещает кеш в принципе, а `rm -rf /root/.cache`
вычищал бы его из точки монтирования.

Проверка на повторной сборке обязательна: если вторая сборка не покажет
заметного ускорения, значит кеш не переживает, и причина ищется отдельно.

## Consequences | Последствия

- Первая сборка после смены версий колёс по-прежнему долгаяя, дальнейшие — нет.
- Кеш занимает место на машине Docker и сам по себе не очищается.
- Версии колёс остаются зафиксированными в аргументах сборки: смена версии
  означает новую закачку, и это ожидаемо.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| `pip download` в каталог на хосте | колёса попадают в образ через `COPY` и раздувают контекст сборки |
| Отдельный том с wheels | нужен ручной шаг перед каждой сборкой, теряется воспроизводимость |
| Оставить `--no-cache-dir` | ровно то, что чинится |
